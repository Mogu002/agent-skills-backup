# Evidence-Rich Workflow

本文件是 `adaptive-skill-creator` 的**高证据参考路径**。

当 Triage 判断用户已提供真实材料（项目文档、SOP、代码、历史记录等），或需要从既有实践沉淀新技能时，进入此工作流。

**核心主张**：从真实材料中提炼可复用流程，而不是依赖泛化模板。

## 适用场景

本工作流用于创建或优化一个 agent skill，使其：
- 具备准确的 `name` 和 `description`
- 保持 `SKILL.md` 简洁聚焦
- 使用渐进式披露，而不是把所有内容塞进主文件
- 贴合真实工作流、术语和 gotchas
- 在后续迭代中依然容易维护

## 与 Evidence-Light 的区别

| 维度 | Evidence-Light | Evidence-Rich (本路径) |
|------|----------------|------------------------|
| 起点 | 从零推导，依赖追问 | 从材料出发，优先推断 |
| 约束来源 | 通用最佳实践 | 真实项目经验 |
| 输出粒度 | 最小可用骨架 | 沉淀完整工作流 |
| 迭代策略 | 先写再试 | 先试再写 |

## 默认立场

- **先读后问**：优先从用户提供的材料中推断，能不问就不问。
- **证据优先**：基于真实项目文档、代码、历史记录来写，而非泛化知识。
- **默认方案明确**：给一条清晰的默认路径，替代方案只在触发条件明确时才提。
- **gotchas 前置**：从失败案例中提炼的坑点，直接写进主文件。

## 核心规则

### 建立在真实经验之上

**不依赖泛化"最佳实践"来合成技能。**

优先基于以下材料来写：
- 与 agent 一起真实完成过的任务
- 项目文档、runbook、schema、配置、代码
- issue 历史、review 评论、反复出现的纠偏
- 真实故障、修复过程与边界案例

如果这个技能没有明确的知识来源，就应当写得更小、更克制。

### 让 `SKILL.md` 保持轻量

`SKILL.md` 只保留每次都要读的内容：
- 技能是干什么的
- 什么时候该用
- 默认工作流
- 最小必要的判断规则
- 指向可选文件的直接引用

细节只有在确实提升聚焦度时才外置。

### 使用浅层渐进式披露

**引用最多只保持一层深度。**

拆分内容时，优先按以下维度之一处理：
- **按深度**：快速开始 vs 进阶细节
- **按领域**：不同业务域或技术栈
- **按条件**：只有特定情况才读取某个文件

推荐：
- `SKILL.md` -> `references/examples.md`
- `SKILL.md` -> `references/api-patterns.md`

避免：
- `SKILL.md` -> `references/index.md` -> 更多导航

### 优先写"方法"，不要只写"答案"

技能应该教会 agent 如何处理一类问题，而不是替某个例子写死答案。

更好的方式：
1. 先看来源材料
2. 再确定默认工作流
3. 提炼约定和 gotchas
4. 围绕这个可复用过程写技能

### 给出一个清晰默认方案

**不要给出一长串等权选项。**

先确定默认路径。只有在触发条件明确时，才提替代方案。

### 让约束强度匹配任务脆弱度

- 多种做法都合理时，保留弹性。
- 顺序脆弱、一致性要求高时，写得更明确。
- 灵活判断和严格步骤可以并存。

### 先定义姿态，再定义内容

高质量 skill 不只是告诉 agent 记住哪些内容，还要规定它处理任务时应采取什么姿态。

应优先写清：
- 动手前先质疑什么前提
- 需要暴露哪些取舍
- 要防哪些常见失败模式
- 最终结果的质量标准是什么

**优先沉淀可迁移的行为约束，而不是领域绑定的话术堆砌。**

### 使用跨领域元问题

当 skill 需要 agent 做判断时，优先给一组可复用、跨领域成立的问题。

例如：
- 这个工作流默认假设了什么？
- 它在真实执行中最可能怎么失败？
- 默认路径是什么，什么情况下应该改走别的路径？
- 什么样的结果才算真的完成得好？

**这样 agent 会先推理，再执行，而不是机械照抄步骤。**

## Frontmatter 规则

> 本节与 evidence-light 路径共享，但强调从真实材料中提炼 description 的写法。

### 必填字段

每个技能都必须有：
- `name`
- `description`

### name

`name` 必须：
- 只使用小写字母、数字和连字符
- 长度在 1-64 个字符之间
- 不能以 `-` 开头或结尾
- 不能包含连续连字符
- 必须与父目录名一致

### description

`description` 是技能的触发表面。

**写法要点**：
- 尽量以"当用户……时，使用这个技能"来表达
- 描述用户意图，而不是内部实现
- 覆盖间接触发场景，而不只是关键词直匹配
- 保持简洁，控制在 1024 字符以内
- 只有在明显可能与别的 skill 冲突时，才补一个简短排除项（`NOT for ...`）

**Evidence-Rich 特有建议**：
- description 应反映真实用户说法（从材料中提取，而非臆测）
- 优先使用用户材料中实际出现的术语和场景描述

推荐：
`当用户想创建或重构一个 agent skill、改进 SKILL.md、优化触发描述，或把可复用工作流沉淀成可维护技能时，使用这个技能。`

不推荐：
`用于创建和优化某个平台专属技能，强调渐进式披露……`

如果两个 skill 很可能命中同一类请求，就加一句简短排除说明。
示例：
`当用户想创建或重构一个 agent skill……时，使用这个技能。NOT for 只改一个提示词、且不会沉淀为可复用工作流的场景。`

### 可选字段

以下 frontmatter 只有在确实需要时才加：
- `license`
- `compatibility`
- `metadata`
- `allowed-tools`

不要把可选字段当装饰项。

## 文件结构

始终使用满足任务需求的最小结构。
规范允许可选的 `scripts/`、`references/` 和 `assets/` 目录。

### 最小结构

```text
skill-name/
`-- SKILL.md
```

### 带引用资料

```text
skill-name/
|-- SKILL.md
`-- references/
    |-- examples.md
    `-- patterns.md
```

### 带脚本

```text
skill-name/
|-- SKILL.md
|-- references/
|   `-- validation.md
`-- scripts/
    `-- validate.sh
```

### 带静态资源

```text
skill-name/
|-- SKILL.md
`-- assets/
    `-- report-template.md
```

## 脚本规则

如果现成工具已经能用一个短而稳定的命令解决问题，就优先用 one-off command。
只有当脚本能明显提升可靠性、复用性或接口清晰度时，才值得打包。

引用脚本时：
- 使用相对于 skill 根目录的路径
- 说明 agent 是要执行还是只需阅读
- 写清预期输入和输出

如果技能包含脚本，优先满足这些要求：
- 接口非交互
- 支持 `--help`
- 错误信息可执行
- 尽量输出结构化数据
- stdout 输出数据，stderr 输出诊断
- 有副作用的操作尽量支持 `--dry-run`
- 可能被重试的操作尽量幂等

## 编写工作流

### 1. 发现

先明确：
- 用途
- 触发场景
- 范围：用户级还是工作区/仓库级
- **知识来源**（本路径的关键差异）
- 产出形态：只写 `SKILL.md`，还是配少量直接支持文件

**仓库特定工作流优先放在工作区或仓库级 skills 目录。**
跨项目复用才考虑用户级全局 skills 目录。
不要把自定义技能写进厂商托管的内置目录。

### 2. 设计

动手前先确定：
- 最终技能名
- description 的措辞（**从真实用户说法中提取**）
- description 应覆盖哪些真实用户说法
- `SKILL.md` 是否已经足够
- 是否需要按深度、领域或条件拆分文件

### 3. 编写

确保技能至少包含：
- 合法 frontmatter
- 清晰的用途说明
- 默认工作流步骤
- 对边缘场景的判断规则
- 指向可选文件的直接引用
- 如果常见错误已知，再补一个简短 gotchas 小节

### 4. 验证

检查以下内容：
- `name` 合法
- `description` 清楚告诉 agent 何时该用
- `description` 以用户意图为中心
- `SKILL.md` 保持简洁和聚焦
- 引用直接且浅层
- 支持文件都有明确理由
- 脚本接口非交互且对 agent 友好
- 可选 frontmatter 都是真正需要的

如果环境中有校验器，可运行：
```bash
skills-ref validate ./skill-name
```

### 5. 迭代

**把技能用于真实任务，再根据执行轨迹修订。**

重点观察：
- description 是否过泛导致误触发
- 选项太多是否造成浪费步骤
- 是否缺少只有失败后才暴露的 gotchas
- 某些指令是否听起来正确但实际无帮助

**成功案例也要回灌。** 稳定有效的做法往往最适合沉淀成工作流。

## 反模式

**避免这些错误**：
- 直接复制通用模板而不做适配
- 用泛化知识代替真实项目材料
- 只定义内容，不定义 agent 的工作姿态
- 把所有细节都堆进 `SKILL.md`
- 还没证明必要就先建很多文件
- 把关键 gotchas 藏进可选引用资料
- 使用深层引用链
- 用绝对路径记录脚本
- 在脚本工作流里依赖交互式提示
- 罗列太多选项却没有默认方案
- 明明存在明显冲突，却不写 `NOT for` 排除说明

## 快速检查清单

> 完成后请对照 `references/shared-checklist.md` 进行最终确认。

交付前确认：
- [ ] `name` 合法且与目录一致
- [ ] `description` 具体且可触发，**基于真实用户说法提炼**
- [ ] 技能建立在真实经验或材料上
- [ ] 技能定义了 agent 的姿态，而不只是内容
- [ ] `SKILL.md` 保持聚焦
- [ ] 关键 gotchas 在主文件可见
- [ ] 引用最多只到一层
- [ ] 支持文件都有明确理由
- [ ] 任何脚本都使用 skill 相对路径且接口非交互
- [ ] 若存在竞争触发场景，已补 `NOT for` 排除说明
- [ ] 没有保留泛化空话
