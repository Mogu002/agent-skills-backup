# Workflow Example

本例用于校准 workflow 题的判断尺度：只覆盖 query 显性需求，不把“通知应该更完整/更好看”之类隐性期待写成硬 requirement。

## Input

```text
type: Workflow
query: 创建工作流，当有电销人员销售等级调整为 L2 或 L3，或者新增了 L2 或 L3 销售等级的销售时，通知其销售管理和邓范鑫。
```

候选检查项：

| # | name | requirement |
|-|-|-|
| 1 | 「电销人员L2L3等级变更新增通知」创建 | 需创建「电销人员L2L3等级变更新增通知」工作流 |
| 2 | 「电销人员L2L3等级变更新增通知」整体流程语义 | 「电销人员L2L3等级变更新增通知」工作流在电销人员表中销售等级新增或变更满足L2/L3条件后，应立即向对应销售管理和邓范鑫发送通知 |
| 3 | 「电销人员L2L3等级变更新增通知」消息内容 | 「电销人员L2L3等级变更新增通知」工作流的消息标题和正文需说明电销人员销售等级变更或新增，并引用触发记录的员工姓名、销售等级和记录链接 |
| 4 | 「电销人员L2L3等级变更新增通知」触发器配置 | 「电销人员L2L3等级变更新增通知」工作流的触发器需配置为‘新增/修改的记录满足条件时’，监听‘电销人员表’的‘销售等级’字段，并需设置销售等级包含L2、L3 |
| 5 | 「电销人员L2L3等级变更新增通知」动作：向销售管理和邓范鑫发送飞书消息 | 「电销人员L2L3等级变更新增通知」工作流的发送飞书消息动作的接收对象需包含邓范鑫以及触发记录中的‘销售管理’字段 |

## Explicit Requirements

- N1：创建一个工作流。
- N2：触发场景包含销售等级调整为 L2 或 L3。
- N3：触发场景包含新增销售等级为 L2 或 L3 的销售。
- N4：通知对象包含对应销售管理。
- N5：通知对象包含邓范鑫。

## Suggested Annotation

| # | action | action_reason | new requirement / reason | review_notes |
|-|-|-|-|-|
| 1 | keep | 对应 N1，检查工作流存在性，无重复或过指定，因此 keep。 | 原 requirement 可作为工作流存在性检查。 |  |
| 2 | keep | 对应 N2-N5，覆盖新增/变更、L2/L3、销售管理和邓范鑫，因此 keep。 | 覆盖新增/变更、L2/L3、销售管理和邓范鑫。 |  |
| 3 | update | 对应通知内容语义，但强制了 query 未指定的消息标题、员工姓名和记录链接，因此 update 改宽。 | 改为：`「电销人员L2L3等级变更新增通知」工作流发送的通知需说明有电销人员销售等级新增或调整为 L2/L3。` 不强制消息标题、员工姓名、记录链接。 | 改宽：移除 query 未指定的消息标题、字段和记录链接要求 |
| 4 | keep | 对应 N2-N3，触发器语义覆盖新增/修改和销售等级 L2/L3 条件，因此 keep。 | 触发器语义覆盖新增/修改和销售等级 L2/L3 条件。 |  |
| 5 | keep | 对应 N4-N5，接收对象与 query 一致，因此 keep。 | 接收对象与 query 一致。 |  |

## Coverage Check

保留和更新后的 requirement 可以回拼出：创建工作流；当销售等级新增为 L2/L3 或调整为 L2/L3 时触发；通知对应销售管理和邓范鑫。没有新增隐性需求。
