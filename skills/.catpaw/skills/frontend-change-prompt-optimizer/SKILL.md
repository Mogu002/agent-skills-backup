# Frontend Change Prompt Optimizer

## 何时使用

当用户不是直接让你改代码，而是希望你把一句较口语化、较模糊的前端修改需求，整理成更适合交给大模型执行的“前端改动语言风格”时，使用这个 Skill。

典型触发方式：
- “帮我把这个前端需求润色一下”
- “整理成适合给模型的前端改动提示词”
- “给我一个前端 UI 修改模板”
- “补上严格技术约束”
- “把我这段自然语言优化成前端改动需求”

如果用户明确要你直接改代码，不要只输出提示词；应优先执行代码任务。

## 核心目标

把用户原始输入转换为：
- 结构化
- 可执行
- 边界清晰
- 默认约束完善
- 尽量减少模型过度改动风险

## 工作原则

1. 保留用户真实意图，不改变业务目标。
2. 不臆造未知事实，例如文件路径、技术栈、接口名、设计稿细节。
3. 未知信息用“沿用现有项目实现/风格/技术栈”这类安全表述兜底。
4. 优先让提示词具备“最小必要改动”的边界。
5. 如果用户输入已很完整，只做轻量结构化整理，不要过度改写。
6. 默认输出中文，且应能直接复制给另一个模型使用。

## 信息抽取槽位

将用户输入整理进这些槽位：
- 目标
- 修改范围
- 当前问题
- 期望改动
- 交互要求
- 视觉要求
- 数据与状态
- 技术约束
- 验收标准
- 输出要求

如果用户没有提供全部信息：
- 缺少技术栈：写“沿用项目现有技术栈与组件库”
- 缺少视觉规则：写“保持与现有设计 token、字号、间距、圆角、阴影一致”
- 缺少交互状态：补齐 `loading / empty / error / disabled`
- 缺少边界条件：补齐“空数据、超长文本、请求失败、慢加载、移动端适配”
- 缺少工程边界：补齐“不要顺手重构无关代码、非必要不引入新依赖、非必要不改全局样式/路由/状态管理”

## 默认技术约束

除非用户明确反对，默认把以下约束并入优化后的提示词：

```text
技术约束：
1. 优先复用现有组件、样式变量和设计 token；
2. 非必要不要引入新依赖；
3. 非必要不要修改接口契约、路由、全局状态和全局样式；
4. 保持现有组件 API 向后兼容；
5. 必须补全 loading、empty、error、disabled 等状态；
6. 保证基本可访问性：可聚焦、可读 label、合理对比度；
7. 兼容移动端和桌面端，不允许出现横向滚动；
8. 改动尽量小、集中、可维护。
```

当用户明确提到“严格一点”“别改太多”“保守修改”“只做局部调整”时，再额外强化：

```text
请做最小必要改动，只解决本次需求，不要顺手重构无关代码。
请先参考当前项目已有组件和样式写法，保持命名、结构、交互和视觉风格一致。
```

## 输出策略

### 默认输出

默认给出两段内容：
1. `优化后的前端改动提示词`：适合大多数情况
2. `严格技术约束版提示词`：适合希望模型更保守时使用

### 输出格式

使用以下结构输出：

```text
优化后的前端改动提示词：
<可直接复制的完整提示词>

严格技术约束版提示词：
<可直接复制的完整提示词>

可补充信息：
- <若有明显缺失，再列 2-5 条>
```

### 写作要求

- 提示词正文应是完整成稿，不要只是提纲
- 保持条目化，便于模型执行
- 不要夹带多余解释
- 如果用户只要一个版本，就只输出对应版本
- 如果用户已经给出明确技术栈，保留并前置
- 如果用户给出文件或页面名，写进“范围”中

## 通用模板

当用户只要求“帮我整理成可执行的前端改动需求”，优先产出下面这个模板的成稿版：

```text
请帮我修改前端代码。

【目标】
我希望把 <页面/组件名> 改成 <目标效果>，主要解决 <问题>。

【范围】
只修改 <文件/目录/页面>。
不要改 <明确禁止改动的内容>。

【现状】
当前存在这些问题：
1. <问题1>
2. <问题2>
3. <问题3>

【期望改动】
请完成以下修改：
1. <改动点1>
2. <改动点2>
3. <改动点3>

【交互要求】
- 点击后：<行为>
- Hover/Focus：<行为>
- Loading：<行为>
- Empty：<行为>
- Error：<行为>
- Disabled：<行为>

【视觉要求】
- 风格：<简洁/企业级/卡片化/极简/高密度>
- 布局：<单列/双列/左右分栏>
- 间距：<紧凑/标准/宽松>
- 颜色：沿用现有设计 token，不要自行发明颜色
- 字体字号：沿用现有排版体系
- 圆角/阴影：与现有组件风格保持一致

【数据与状态】
- 使用已有接口/数据结构：<接口或状态来源>
- 不改变字段含义和接口契约
- 需要处理边界情况：<空数据/超长文本/请求失败/慢加载>

【技术约束】
- 技术栈：<React/Vue/Next/Tailwind/Ant Design/...>
- 优先复用现有组件，不新增重复组件
- 非必要不要引入新依赖
- 非必要不要改动全局样式、路由、状态管理
- 保持向后兼容，不要破坏现有 props / API
- 代码风格遵循项目现有写法

【验收标准】
- 页面在 <移动端/桌面端> 显示正常
- 不出现横向滚动
- 交互状态完整
- 可访问性基本合格
- 不影响现有功能
- 改动尽量小而清晰

【输出要求】
请直接修改代码，并说明：
1. 改了哪些文件
2. 为什么这样改
3. 还有哪些风险或可选优化
```

## 严格技术约束版模板

当用户强调“严格约束”“避免改多”“更工程化”“更适合直接丢给模型执行”时，输出下面这个风格的成稿版：

```text
请帮我修改前端代码，并严格遵守以下边界。

【目标】
将 <页面/组件/模块> 调整为 <目标效果>，重点解决 <问题>。

【修改范围】
- 仅允许修改：<页面/组件/局部样式/相关文件>
- 不要修改：<接口契约/路由/全局主题/全局样式/无关模块>

【具体改动】
1. <改动项1>
2. <改动项2>
3. <改动项3>

【交互与状态】
必须完整处理以下状态：
- loading
- empty
- error
- disabled
- success

并补充以下交互细节：
- 点击反馈明确
- 表单/按钮防重复触发
- 错误提示靠近问题区域
- 超长文本、空数据、慢请求有合理展示

【视觉与一致性】
- 保持与现有设计系统一致
- 复用现有组件、样式变量、设计 token
- 不自行发明新的颜色、字号、阴影、圆角体系
- 保持现有命名、结构、交互和视觉风格一致

【技术约束】
1. 优先复用现有组件、hooks、工具函数；
2. 非必要不要引入新依赖；
3. 非必要不要新增重复组件；
4. 非必要不要改动接口参数、数据结构、对外 props、事件协议；
5. 保持向后兼容；
6. 非必要不要调整全局样式、路由、状态管理；
7. 保证基本可访问性：可聚焦、label 清晰、对比度合理；
8. 兼容移动端和桌面端，不允许横向滚动；
9. 仅做最小必要改动，不顺手重构无关代码；
10. 改动应保持可维护，避免临时性堆叠写法。

【验收标准】
- 功能行为符合需求
- 现有功能不回归
- 视觉风格与项目一致
- 状态完整
- 响应式正常
- 改动集中、清晰、易审查

【输出要求】
请直接修改代码，并在完成后说明：
1. 修改了哪些文件
2. 每个改动点解决了什么问题
3. 是否存在风险点或后续可优化项
```

## 改写流程

按下面顺序处理用户输入：

1. 识别用户原始诉求：是页面改版、组件微调、交互优化、样式统一，还是工程性约束补全。
2. 抽取已知信息：页面、组件、问题、目标、限制、技术栈。
3. 补齐缺省槽位：只补工程上安全的默认项，不虚构业务细节。
4. 生成通用版提示词。
5. 生成严格技术约束版提示词。
6. 如果存在明显信息空缺，再追加“可补充信息”。

## 信息缺失时的处理

只有在缺失信息会直接影响提示词可执行性时，才提示补充。优先少问，先给可用版本。

优先补充的问题类型：
- 改动对象是哪个页面/组件
- 是否有明确不能动的模块
- 是否指定技术栈或组件库
- 是否更看重视觉、交互还是工程约束

如果这些信息没有，也可以直接输出带安全默认值的版本。

## 禁止事项

不要：
- 凭空编造文件路径、接口名、组件名
- 把用户“局部优化”扩写成“大规模重构”
- 输出过于泛泛的空话，如“优化体验”“提升观感”但没有具体执行点
- 省略状态处理和工程边界
- 在用户未要求时输出与提示词无关的大段方法论

## 示例

### 示例 1

用户原话：

```text
我想让列表页筛选区更清晰一点，移动端现在很乱，按钮也不明显，帮我整理成适合给模型改前端的说法。
```

期望输出风格：

```text
优化后的前端改动提示词：
请帮我修改用户列表页的筛选区域。

【目标】
让筛选区更清晰、更紧凑，减少首屏占用，同时提升移动端可用性。

【范围】
只修改列表页的筛选栏和相关局部样式，不要改表格逻辑、接口请求逻辑和全局样式。

【现状】
当前存在这些问题：
1. 筛选项信息层级不清晰；
2. 按钮主次不明确；
3. 移动端换行和堆叠混乱；
4. 缺少完整的状态反馈。

【期望改动】
1. 重新整理筛选项布局，提升信息层级；
2. 明确查询与重置按钮的主次关系；
3. 移动端改为更稳定的单列或分组堆叠；
4. 补齐 loading、empty、error、disabled 状态展示；
5. 保持现有字段和查询逻辑不变。

【技术约束】
- 沿用项目现有技术栈、组件库和样式体系；
- 优先复用已有组件，不新增重复组件；
- 非必要不要引入新依赖；
- 非必要不要修改接口契约、路由和全局样式；
- 做最小必要改动，不顺手重构无关代码。
```

### 示例 2

用户原话：

```text
帮我把这个需求写严格一点：把弹窗好好优化一下，别改太多。
```

期望输出风格：

```text
严格技术约束版提示词：
请帮我优化现有弹窗组件，并严格遵守以下边界。

【目标】
在不改变原有业务逻辑的前提下，提升弹窗的可读性、操作清晰度和状态完整性。

【修改范围】
- 仅允许修改弹窗组件及其局部样式；
- 不要修改弹窗对外 props、事件协议、业务提交流程和全局样式。

【具体改动】
1. 优化弹窗标题、正文、操作区的信息层级；
2. 明确主按钮与次按钮样式和位置；
3. 补齐 loading、disabled、error 状态；
4. 保持现有调用方式不变。

【技术约束】
1. 优先复用现有组件和样式变量；
2. 非必要不要引入新依赖；
3. 保持 API 向后兼容；
4. 只做最小必要改动，不顺手重构无关代码；
5. 保持现有命名、结构、交互和视觉风格一致。
```

## 最终要求

你的输出必须让用户可以直接复制给另一个模型使用；除非用户要求，否则不要把结果写成“思考过程”或“分析报告”。
