# 学城笔记 — 笔记本管理 & 智能问答

通过 CLI 管理笔记本、批量添加文档（学城或公网网页）、上传本地文件（PDF/Word/Markdown/TXT）或直接添加文本内容为知识来源，并基于笔记本知识库进行智能问答（RAG）。认证自动处理。

本技能不仅处理“笔记本管理”，也处理“把内容/文件保存到 nb”这一类目标型请求。只要用户目标是把资料放进笔记本，就应优先由本技能承接，再决定采用 `addFileSources` 还是 `addContentSource`，而不是先走通用阅读链路。

## 概念与边界

**本技能唯一管辖对象**：MBookLM 笔记本（知识库容器），即用户在 [nb.sankuai.com](https://nb.sankuai.com/) 创建的笔记本。

**平台容量限制**（规划任务前须知）：
- 每个用户最多创建 **10 个**笔记本
- 每个笔记本最多包含 **5000 个**来源（文档）

**笔记本权限说明**：
- 用户的笔记本列表中除自己创建的笔记本外，还可能包含他人分享给自己的笔记本
- `selectNotebookList` 返回的每个笔记本对象包含 `canEdit` 字段：`true` 表示可编辑（含上传来源），`false` 表示只读
- **要求**：执行 `addSources` / `addContentSource` / `addFileSources` 前，必须核查目标笔记本的 `canEdit` 字段，`canEdit=false` 时立即停止并告知用户
- CLI 默认输出中，`canEdit=false` 的笔记本会标注 `[只读]`，让 Agent 可直接识别
- 本期新增群权限能力：仅支持**给群开通浏览权限**；对应 CLI 指令为 `edi mbooklm addGroupPermission --notebookId <id> --groupId <groupId>`

**群权限管理规则**：
- 如果用户是在**大象群里创建了笔记本**，创建成功后需要**立即为当前群开通权限**
- 默认权限固定为**浏览权限**
- 本期**仅支持群权限新增**，不支持群权限修改/删除，也不支持用户/组织权限在 skill 层透出
- 执行时使用 `addGroupPermission`，不得自行拼接服务端 HTTP 请求

**与学城文档的区别及歧义消解规则**：

| 用户说的词 | 默认归属 | 例外（需转交其他技能） |
|---|---|---|
| 「笔记」「笔记本」「学城笔记」「学城笔记本」「我的笔记」「MBookLM」 | ✅ 本技能直接处理，**无需向用户确认** | 用户明确说「学城文档」「wiki 页面」「collabpage」「KM 文章」「创建/编辑文档」时，转交 `citadel` 或 `km-collabpage-creator` |
| 「nb」「我的nb」「nb里」「问nb」「nb列表」「新建nb」「往nb加」「问下nb」「nb里有」「取消nb」「不用nb了」等含 `nb` 的学城笔记本操作短语 | ✅ 本技能直接处理，**`nb` 是「学城笔记本」的口语简称，出现即触发本技能；解析笔记本名时不含 `nb` 本身** | 若 `nb` 明显不在笔记本操作上下文中（如「这个方案 nb」「nb 牛逼」等感叹语气），不触发本技能 |

> **歧义时的行为准则**：凡用户提到上表左列词汇，**直接按 MBookLM 笔记本处理，不得向用户反问确认**。仅当用户明确使用右列词汇时才转交其他技能。

## 与 file-download 的协作规则

- 用户目标是"保存到 nb/笔记本"时，必须优先进入本技能，不因文件可读就先走阅读链路
- `file-download` 若已下载文件，下一跳必须回到本技能继续处理；不得停在下载结果或转去阅读
- 下载后用户尚未指定目标笔记本时，继续引导用户选择，完成"保存到 nb"的最终动作
- **【强制】文件名是时间戳时，必须通过 `--displayNames` 传入原始文件名**：若文件路径的 stem（去掉扩展名后的部分）全为数字且长度在 8-13 位（如 `1709697600.pdf`、`1709697600123.pdf`），则判定为时间戳重命名；此时**必须**通过 `--displayNames` 参数传入用户可识别的原始文件名，否则笔记本来源标题将显示为纯数字。原始文件名的获取优先级：① 消息卡片 / 附件卡片中的原始文件名；② 用户在对话中明确提到的文件名；③ 前序步骤（如 file-download）返回的元数据中的文件名；④ 若无法识别，不得自行猜测，应先追问用户

> `nb` 是 `mbooklm`（学城笔记本技能）的快捷别名。`nb` 默认指向当前笔记本；若当前笔记本为空，则按「目标笔记本解析」流程处理。高频会话说法见 [references/chat-quick-help.md](references/chat-quick-help.md)。

## 当前笔记本

**当前笔记本**是本轮会话内的默认目标，用于在用户未明确指定笔记本时自动代入。

### 生命周期

| 事件 | 触发方式 | 结果 |
|---|---|---|
| **设定** | 用户说「换成 xxx」「以后用 xxx」「以后就用 xxx」「切到 xxx」「切到 xxx 笔记本」 | 解析目标笔记本，设为当前笔记本 |
| **自动更新** | 本轮成功执行目标唯一明确的查询、导入或问答类命令（如 `mbooklmChat` / `addSources` / `listSources` / `searchNotebookDocs`） | 目标笔记本自动成为当前笔记本 |
| **不触发更新** | `selectNotebookList` / 候选澄清阶段 | 无变更 |
| **清空** | 用户说「清空当前笔记本」「取消当前笔记本」「不用当前笔记本了」「取消默认」 | 当前笔记本置空 |
| **初始** | 会话开始 | 为空，无当前笔记本 |

### 使用规则

- **任意时刻只能有一个当前笔记本**，新设定或切换会直接覆盖旧值
- 当前笔记本在 **当前对话线程** 内有效，**不跨会话持久化**
- 用户未明确指定笔记本时，将当前笔记本作为默认目标；若当前笔记本为空，则按「目标笔记本解析」流程处理
- 显式切换笔记本时，无论读写操作，均覆盖当前笔记本
- 用户主动询问「当前笔记本是哪个」「当前默认笔记本是哪个」时：有则展示，无则回复「当前没有设置；你可以直接指定笔记本名，或先说『我的 nb 列表』来选择」
- **推荐心智模型**：`nb = 当前笔记本`；当前笔记本等于最近一次成功聚焦的唯一目标笔记本；若当前为空，则走「目标笔记本解析」流程

## 核心决策：目标笔记本解析

当需要确定目标笔记本时，按以下决策矩阵执行。

> 若「核心决策」「执行策略」「典型场景」出现表述重叠，以**核心决策**和**执行策略**为准；典型场景仅作示例，不额外引入新规则。

### 决策矩阵

| 是否指定笔记本名 | 当前笔记本状态 | 匹配情况 | 意图类型 | Agent 行为 |
|---|---|---|---|---|
| 是 | 任意 | 精确命中 / 归一化命中 | 任意 | 直接使用命中的笔记本 |
| 是 | 任意 | 容错命中（唯一高置信候选） | 读操作（`mbooklmChat` / `listSources` / `getNotebook` / `searchNotebookDocs` / `getSourceContent`） | 自动纠正，直接使用 |
| 是 | 任意 | 容错命中（唯一高置信候选） | 写操作（`addSources` / `addContentSource` / `addFileSources`） | 纠正后需用户确认 |
| 是 | 任意 | 多候选（≥2 个） | 任意 | 列出最多 3 个候选，等用户选择 |
| 是 | 任意 | 完全未命中 | 写操作（`addSources` / `addContentSource` / `addFileSources`）或显式设定当前笔记本 | **直接创建该笔记本**，无需询问；创建成功后继续原始意图 |
| — | — | 命中但 `canEdit=false` | 写操作（`addSources` / `addContentSource` / `addFileSources`） | **停止执行**，告知用户该笔记本为只读分享无法上传来源，并提示选择自己的笔记本或新建 |
| 是 | 任意 | 完全未命中 | 读操作（`getNotebook` / `listSources` / `mbooklmChat` / `searchNotebookDocs` / `getSourceContent`） | **不创建**，告知用户未找到并提示可新建 |
| 否 | 有当前笔记本 | — | 任意 | 直接使用当前笔记本 |
| 否 | 为空 | — | 查看笔记本列表 | 直接调用 `selectNotebookList` |
| 否 | 为空 | — | 其他意图 | 先调用 `selectNotebookList`；若仅有一个笔记本则直接采用并告知用户，若有多个则展示最多 5 条供用户选择，选择后继续执行原始意图（详见「匹配规则详解」第 4 点） |

### 匹配规则详解

1. **精确/归一化命中**：名称完全一致，或去掉「笔记本」「知识库」「笔记」等通用修饰词后唯一命中
2. **容错命中**：存在唯一高置信候选（错别字、同音字等）时自动采用
3. **多候选澄清**：列出最多 3 个候选，等用户选择；编号仅对本次澄清有效
4. **无名字线索且当前笔记本为空**：先调用 `selectNotebookList`；若仅有一个则直接采用并告知，若有多个则展示最多 5 条供用户选择，并附原始问题上下文

### 完全未命中时的处理

用户**明确指定了目标笔记本名称**，但现有笔记本中完全找不到时：

- **写操作（`addSources` / `addContentSource` / `addFileSources`）或显式设定当前笔记本（如「以后用 xxx」「切到 xxx」）**：
  - **直接调用 `createNotebook` 创建该笔记本，无需追问**
  - 创建成功后继续原始意图，并将新笔记本设为当前笔记本
  - 若创建失败（达到上限），立即按「失败与降级策略」处理

- **读操作（`getNotebook` / `listSources` / `mbooklmChat` / `searchNotebookDocs` / `getSourceContent`）**：
  - **不要静默创建空笔记本**
  - 应明确告知「未找到 [xxx] 笔记本」，并提示用户可直接新建或在后续导入文档时自动创建

## 执行策略

### 来源获取策略（批量导入场景）

当用户说「帮我把某个网站/学城空间最近一个月的文章都存入 xxx 笔记本」时：

- `addSources` 只需要 URL 列表；标题、正文、摘要只在筛选、去重或展示结果时按需获取
- 优先用轻量方式提取 URL；只有静态抓取拿不到完整 URL、需要登录/点击/滚动/执行 JS、或目标是学城内部系统时，才升级到专业工具
- 目标只是导入笔记本时，不要为了补齐文章详情而额外逐篇抓正文

最小流程：
1. 获取 URL 列表
2. 按用户条件过滤
3. `createNotebook`（若需要）
4. `addSources` 提交；超过 100 个 URL 时按每批 ≤100 串行调用，并在每批确认 `totalCount > 0` 后再继续
5. **记录本次提交时间**：第一批 `addSources` 调用前，用 `Date.now()` 记录当前 Unix 毫秒时间戳，保存在上下文中；若用户后续发起对账，直接透传给 `retryBatchSources --submittedAt`

### 批量导入后的结果确认与恢复

当用户批量导入 URL 后，若出现「右侧来源数和左侧文件数对不上」「有几条没进来」「帮我重试失败的来源」这类诉求时：

1. 先明确：`addSources` 成功返回只代表**已提交入库**，后续解析/向量化仍是异步过程
2. 若用户只是想知道“现在结果怎样了”，**必须重新调用** `listSources` 查看来源状态，不能直接复述上一轮结果或导入回执
3. 若用户明确要**对账 + 重试本次批量导入**，且能拿到本次原始 URL 列表，则使用 `retryBatchSources`

`retryBatchSources` 的行为边界：
- 会先查询笔记本当前来源列表，与本次 URL 列表做对账
- 对已入库且状态为 `FAILED/ERROR` 的来源，调用服务端重试接口
- 对本次 URL 列表中存在、但当前笔记本里找不到的 `missing` 项，默认只汇报，不自动重新执行 `addSources`
- 对仍处于 `PROCESSING` 的来源**不自动重试**，只提示用户稍后再看
- 只有用户明确要求“把缺失的也重新导入”时，才传 `--retryMissing true`

使用条件与优先级：
- **必须**能拿到本次原始 URL 列表；拿不到时，不得猜测哪些 URL 缺失
- **必须**透传本次提交时间给 `--submittedAt`；若上下文中有记录的时间戳，直接使用；若遗失，告知用户对账结果可能偏保守（同 URL 旧记录可能干扰判断）
- 若用户只说“重试失败来源”，但没有原始 URL 列表，只能先 `listSources` 告知状态，必要时请用户补本次 URL 列表后再执行 `retryBatchSources`
- 若用户只说“重试失败来源”，默认**只重试 `FAILED/ERROR`**，不要顺带重新导入 `missing`；除非用户明确同意“缺失项也重新导入”
- 若用户说「别用缓存 / 再查一次 / 最新状态 / 现在怎么样了」，一律视为**强制实时查询信号**：必须重新调用 `listSources`，不得沿用会话中的旧总结

用户视角下的推荐说法：
- 「刚才那批链接有几条没进来，帮我检查并重试」
- 「这个笔记本里刚导入的那批来源现在是什么状态」
- 「帮我把这批导入失败的来源重试一下」
- 「刚才导入 196 条，帮我对账看看哪些失败了」

### 添加内容策略（用户直接提供内容场景）

当用户直接提供文本（如对话中粘贴的字符串内容、个人笔记、代码片段）时，使用 `addContentSource`：
1. `createNotebook`（若需要）
2. `addContentSource` 一次提交

该模式不需要抓取或预处理，优先于先爬 URL 再导入。

### 来源形式与入库方式决策

三种入库命令按来源形式决定：

| 场景 | 使用命令 |
|---|---|
| 用户提供 URL（学城链接、公网网页、批量 URL 列表） | `addSources` |
| 用户直接提供文本内容，或工具已拿到需加工后保存的正文 | `addContentSource` |
| 用户提供 PDF / Word 本地文件 | `addFileSources` |
| 用户提供 Markdown / TXT 文件，且无“按原文件保存”要求 | `addContentSource` |
| 用户提供 Markdown / TXT 文件，且明确要求按文件上传 | `addFileSources` |

高风险锚点：
- `PDF / Word` 默认保留文件语义；当前轮存在附件、文件卡片、可访问路径或原文件引用时，必须优先绑定并走 `addFileSources`
- `.md / .txt` 默认允许按文本入库；只有在用户明确强调「按原文件保存 / 不要读取内容 / 就按文件上传」时，才走 `addFileSources`
- 只有用户**直接在对话里粘贴 Markdown 文本内容**，而不是提供 `.md` 文件时，才直接按 `addContentSource` 处理
- 文件已由上游步骤下载到本地，而用户目标仍然是“保存到 nb/笔记本”时，应继续交给本技能处理，不默认进入阅读链路
- 指代不清时不能猜：`PDF / Word` 必须先澄清或请用户重发；`.md / .txt` 只有在能稳定拿到正文时才可直接走 `addContentSource`

> ⚠️ **「保存/存到笔记本」歧义消解规则**（按优先级顺序判断）：
> 1. **当前轮消息里有可见附件 / 文件卡片 / 明确文件名时，只能以当前轮附件为准**；用户说「这个文件」「上面的两个文件」「这个附件」时，**优先绑定当前轮附件集合，禁止从历史对话、长期记忆或更早轮次里回填旧文件**
> 1a. **若平台把“附件消息”和“文字指令消息”拆成同一用户连续发送的两条相邻消息**（例如先发 2 个附件，紧接着再发「nb 帮我保存这两个文件到 MDP」），则这组相邻消息应视为**同一轮附件上下文**；不得因为文字指令这一条本身不带附件卡片，就误判为“当前轮没有附件”
> 2. 上下文中有 `PDF / Word` 文件路径、文件名、扩展名（`.pdf` / `.docx` / `.doc` 等）或明确附件语义 → `addFileSources`
> 3. 上下文中有 URL（`http://` / `https://` / `km.sankuai.com` 等） → `addSources`
> 4. 上下文中有明确的文字内容，或对象是 `.md / .txt` 且已可稳定获取正文 → `addContentSource`
> 5. **以上线索均不存在（如「把这个保存到笔记本」「保存一下」等纯指代）** → **不得猜测，直接追问**：「请问你想保存的是文件、文字内容，还是网页链接？」

**附件绑定硬约束**：
- 若当前轮有 1 个附件，用户说「这个文件 / 这个附件」时，默认指向**当前轮这个附件**
- 若当前轮有多个附件，用户说「上面的俩文件 / 这两个附件 / 都存进去」时，默认指向**当前轮全部附件**
- 若当前输入不带附件卡片，但其**紧邻上一条同一用户消息**仅包含附件，且中间无其他用户/助手打断，则仍应把这些附件视为**当前轮附件**
- 若当前轮有多个附件，但用户只说「这个文件」且无法唯一定位到其中一个时，**只允许在当前轮附件范围内追问，不得改绑到历史文件**
- 若在检查了**当前消息 + 紧邻上一条同一用户附件消息**后仍找不到附件，或当前轮有附件但用户指代目标**仍不明确**：
  - 对 `PDF / Word`：**必须先确认文件名或请用户重发文件**，不得自动改用历史文件
  - 对 `.md / .txt`：若能稳定拿到正文，可直接改走 `addContentSource`
- 若当前轮提供的是 `.md` / `.txt` 附件，默认允许按**文本内容**入库；只有用户明确要求“按文件上传/不要读取内容”时，才继续保留为文件上传对象
- **禁止**因为历史消息里出现过文件名、路径、代码文件或记忆项，就把它们当作本轮上传对象

### deleteNotebook 规则

- 删除前必须二次确认：先明确复述即将删除的笔记本名称，只有用户明确确认后才执行
- 仅允许删除本人创建的笔记本
- 对 `canEdit=false` 的分享笔记本直接拒绝
- 对非本人创建但可编辑的协作笔记本，也默认拒绝，并提示用户前往官网确认
- 若删除的是当前笔记本，则清空当前笔记本
- 若删除的不是当前笔记本，则当前笔记本保持不变
- 删除失败时不得自动重试、不得自动切换到其他笔记本、不得创建新笔记本

### 群权限管理规则

- 若本轮是在大象群上下文中成功创建了笔记本，创建完成后应继续执行 `addGroupPermission`
- `addGroupPermission` 所需参数为：
  - `notebookId`：来自刚创建成功或已解析出的目标笔记本
  - `groupId`：当前群 ID
- 权限级别固定为浏览权限，Agent 不需要向用户追问权限等级
- 推荐按两步链路对外表述：先说明“笔记本已创建”，再说明“已为当前群开通浏览权限”
- 若两步都成功，应使用完成态话术，例如“已创建笔记本，并已为当前群开通浏览权限”
- 若缺少当前群 `groupId`，只追问 `groupId`
- 若 `addGroupPermission` 失败，应明确告知“笔记本已创建，但当前群权限开通失败”，避免让用户误以为整条链路都失败
- 若 `createNotebook` 失败，则不得继续执行 `addGroupPermission`
- 若用户只是普通创建笔记本、且当前并非大象群上下文，则只执行 `createNotebook`，不要额外提群权限

### 会话上下文复用与重查规则

**可直接复用**：
- 当前笔记本已唯一确定，且用户未切换目标笔记本
- 紧邻上一轮的 `searchNotebookDocs` 结果仍在当前会话上下文中
- 用户使用「这篇」「上面那篇」「获取全文」「查内容」等明显承接上一轮检索结果的表达

**必须重查**：
- 用户显式切换了笔记本，或当前笔记本为空
- 上一轮检索结果无法唯一匹配用户指代
- 中间已经经过多轮无关对话，引用不再稳定
- 用户明确说「重新查一下」「再搜一遍」「刷新列表」

**执行要求**：
- 已解析出唯一 `targetNotebook` 后，不要为同一目标重复调用 `selectNotebookList`
- 已保留上一轮检索结果和 `sourceId` 映射时，不要为了「这篇 / 获取全文」先做无意义的重复检索
- 只有在上面列出的“必须重查”条件出现时，才重新执行查询命令

### 失败与降级策略

当 `createNotebook` 返回空 notebookId（如 `❌ 笔记本数量已达上限`）时：
- 立即停止，不重试、不猜测原因、也不继续后续步骤
- 展示现有笔记本列表
- 提示用户先删除旧笔记本或复用现有笔记本；必要时再前往官网处理
- 可补充一句引导：或者告诉我用现有哪个笔记本来存放，我直接导入。

用户选择复用某个笔记本后，直接进入 `addSources` 或 `addContentSource` 流程，**无需再次查询笔记本列表**（已有 notebookId）。

## 最小典型场景

以下场景只保留最容易跑偏的 3 类，其他会话表达按上方「目标笔记本解析」「意图路由」「执行策略」执行。

### 场景 1：当前笔记本为空时的选择流程

> 用户说："问 nb，发布流程是什么？"

- 当前笔记本为空、且用户未提供名称线索时：先执行 `selectNotebookList`
- 若只有 1 个笔记本：直接采用并继续原问题
- 若有多个笔记本：列出最多 5 个候选，让用户选择后继续执行
- 选择完成后，所选笔记本成为当前笔记本

### 场景 2：显式指定不存在的笔记本

> 用户说："把这些文档加到 过程管理 笔记本"

- 这是“显式指定目标笔记本 + 写操作”场景：若现有列表完全未命中，直接 `createNotebook`
- 创建成功后继续原始写操作，并将新笔记本设为当前笔记本
- 若创建失败（达到上限），立即按「失败与降级策略」处理
- 若原始意图是读操作（如“看看 过程管理 里有哪些文档”），则不静默创建，只提示未找到

### 场景 2.1：在大象群里创建笔记本

> 用户说："在这个群里建一个发布知识库"

- 先执行 `createNotebook`
- 创建成功后，若当前会话可拿到群上下文，立即执行 `addGroupPermission`
- `addGroupPermission` 固定使用当前群的 `groupId`；权限固定为浏览
- 对外说明时要区分两步结果：笔记本创建成功、群权限是否开通成功
- 若当前群上下文缺少 `groupId`，只补问群 ID；无需补问群名称
- 若用户明确说“不用给群开权限”，则只保留创建结果，不强推第二步

### 场景 3：先检索再精读 / 直接点名精读

> 第一轮："搜一下 nb 发布流程"
>
> 第二轮："读一下这篇" / "获取 Spring AI Agents 接入手册 全文"

- 若紧邻上一轮已有 `searchNotebookDocs` 结果，且用户说“这篇 / 上面那篇 / 获取全文 / 查内容”等明显承接表达：
  - 唯一匹配时直接执行 `getSourceContent`
  - 多候选且不唯一时先让用户选择
  - 无法匹配时重新执行 `searchNotebookDocs`
- 若没有上一轮检索结果，但用户直接点名标题（如“帮我精读《MDP 版本发布规范》”）：
  - 先执行 `searchNotebookDocs`
  - 唯一命中则直接执行 `getSourceContent`
  - 多候选则让用户选择
  - 未找到则提示用户换关键词或确认来源

**共用规则**：
- `sourceId` 默认不展示给用户
- 「这篇 / 这个来源 / 上面那篇」只在当前会话内、且上一轮检索结果仍可信时才可直接复用
- 若中间已经经过多轮无关对话、用户换了笔记本，或引用不再唯一，则必须重新检索

## 约束

- 所有命令的 `notebookId` 必须从 `selectNotebookList` 或 `getNotebook` 返回结果中获取，**不得自行构造或猜测**
- 执行 `addSources` / `addContentSource` / `addFileSources` 前，**必须核查**目标笔记本的 `canEdit` 字段；`canEdit=false`（列表中标注为 `[只读]`）的笔记本为只读分享，**禁止向其上传来源**，应停止并提示用户选择可编辑的笔记本或新建笔记本
- 缺少关键参数时只追问必要字段（目标笔记本 / name / query），不给笼统报错
- `addSources` 的 `urls` 参数支持学城（km.sankuai.com）链接及公网网页；非公开或无法访问的 URL 会导致 `totalCount=0`
- `addContentSource` 的 `content` 参数接受字符串内容，单次只能添加一条内容；不支持 URL；推荐使用结构化文本以提升阅读和问答效果
- **风控**：同一 session 内工具调用不超过 20 次/分钟；`addSources` / `addContentSource` / `addFileSources` 均必须串行调用，禁止并行

## 输出规范

### 通用展示原则

- 链接统一用 Markdown；来源无 URL 时可直接展示标题或摘要
- 默认不展示内部 ID（如 `notebookId`、`sourceId`、`sessionId`）；仅在用户明确要求时才展示
- 面向用户展示状态时，统一使用中文：`已成功`、`处理中`、`解析失败`、`笔记本中未找到`；不要直接向用户暴露 `ACTIVE`、`PROCESSING`、`FAILED`、`ERROR` 等内部枚举
- 解析状态只在异常时提示：`处理中` → `⏳ 解析中，暂不可用于问答`，`解析失败` → `❌ 解析失败，可重新导入`
- `searchNotebookDocs` 默认不展示 `sourceId`，但应将其保存在上下文中，便于后续「看这篇」「读一下这个」直接触发 `getSourceContent`

### 特殊命令例外

- `getSourceContent`：将正文**原样透传**，不改写、不重组；标题用 Markdown 标题，`id` 不展示
- `mbooklmChat`：将回答**原样透传**，不改写、不重组；参考来源优先展示 Markdown 链接，超过 3 条时只展示前 3 条并说明另有 N 条

### 回复结构

每次回复结构如下，各块均**按需出现，无内容则省略，不占位**：

```
[回答内容]

---                    ← 仅下方至少有一块内容时出现，否则省略
✨ 你可能想问：        ← 有明确下一步操作或追问方向时出现
- <用户口吻的可点击短句（优先疑问句）>
- 「💡 小提示：你可以直接用 `nb` 代替「学城笔记本」…」   ← 仅本会话首次检测到全称词汇时追加

🎯 当前笔记本：[笔记本名称](https://nb.sankuai.com/notebook/xxx)
               ← 本轮操作有明确目标笔记本时出现（切换笔记本时改用下方「切换格式」，不用此行）
```

**各块出现条件详述**：

| 块 | 出现条件 | 不出现条件 |
|---|---|---|
| 推荐问 | 有明确的下一步操作或追问方向 | 无自然延伸（如切换/清空笔记本等纯状态操作） |
| 当前笔记本（普通格式） | 本轮成功执行目标唯一明确的查询、导入或问答类命令 | `selectNotebookList` / 候选澄清阶段 / 本轮执行后当前笔记本仍为空（**不展示「当前笔记本为空」等空状态提示**）|
| 当前笔记本（特殊格式） | 切换/首次设定时；清空时 | 其他情况 |
| `nb` 快捷别名引导 | 本轮用户输入含全称词汇（「学城笔记本」「mbooklm」「MBookLM」「笔记本」「我的笔记本」等），且**本会话首次** | 已展示过（每会话仅一次）；用户已使用 `nb` 触发本技能 |

**当前笔记本状态变化时的特殊格式**（替代普通 `🎯 当前笔记本：` 行）：

```
🎯 当前笔记本已切换为 [xxx](...)，后续可直接说「问 nb …」「往 nb 加…」。   ← 切换/首次设定时
🎯 当前笔记本已清空，后续需指定笔记本。                                 ← 清空时
```

### 推荐问规则

用**用户第一人称、可直接点击的短句**写，优先疑问句。当前笔记本已知时，必须用实际名称替换占位符。

- 每次最多给 `1–3` 条；纯状态操作（切换、清空）默认不追加
- 若本轮已通过 `🎯 当前笔记本...` 明确说明当前状态，不再重复引导
- 导入、上传、问答或检索后，优先推荐紧邻下一步动作
- 查看帮助时，当前笔记本为空优先给首用动作；当前笔记本已知优先给连续动作

**引导使用 `nb` 快捷别名**：触发条件见「各块出现条件」中的 `` `nb` 快捷别名引导 `` 行。若本轮已经通过 `🎯 当前笔记本...` 告知用户后续可直接说 `nb`，则**不再重复展示**本提示。否则展示内容：
