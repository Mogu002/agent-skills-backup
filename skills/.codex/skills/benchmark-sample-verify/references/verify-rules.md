# 核验完整判据与逐项清单

本文件是 benchmark 样张核验的详细规则，SKILL.md 的工作流程落到这里的具体判据。每次核验前通读。

## 真值三件套怎么读

| 字段 | 作用 | 核验时怎么用 |
|---|---|---|
| 指令 | 给 Agent 的任务原文 | 看任务要在哪个库、筛什么、输出什么列 → 推断真考察库和 Gold 口径 |
| 样张设计思路 | 设计者的埋点方案 | 规模档、复用/新增字段、附件命中列、算子链、Gold 行、正负样本数、唯一验证依据 → 核验的对照表 |
| 考察点 | 要考的能力 | 多模态(pdf/图片)、行数门槛、Semantic Operator → 决定要不要下附件、核多深 |

设计思路常见结构化小节（见过的写法）：`【规模对齐】【复用字段】【附件命中】【主算子/算子链】【Gold】【唯一验证依据】【正负样本】`。逐小节对照副本实现。

## 坑1：副本编号 ≠ 库语义顺序

**现象**：设计思路/备注常按"副本01=第一个库、副本02=第二个库"描述，但副本链接里的编号（副本01/02/08/18/19）**不保证**和库语义顺序一致。实战中真考察库经常在副本08/18/19，而副本01/02 固定被"投研·上市公司财报库""政务公文档案库"占着做陪跑干扰。

**判据**：
- 必须对每个副本 base_token 执行 `+table-list` 看**真实表名**，不能靠编号或链接文字猜。
- 把真实表名与"指令/设计思路要考的库"对齐，才能确定真考察库。
- 真考察库通常 `rev` 较高（被改过），但 rev 不是唯一信号（陪跑表也可能 rev 高），**以表名语义为准**。
- 若设计思路/备注声称的"副本X=某库"与实测不符 → 这是一个**定位错位**问题。是否判"有问题"由用户口径定；若判有问题，机评要写清"声称副本X实为A库，真考察库B在副本Y"，而不是写成"没做"（容易误导）。

## 坑2：只读表字段会漏判，多模态判据藏在附件里

**现象**：如 Q113"发票抬头开错"，判据是"发票照片购买方名称 vs 记账主体不一致"。但"发票照片购买方名称"只存在于 receipt_img 图片里，表里**没有这一列**。只比对表字段（记账主体 vs 往来对象）根本发现不了开错。

**判据**：
- 考察点含"pdf/图片"或"Semantic Operator"，或指令说"从照片/扫描件读出X" → 判据在附件，必须下载看图。
- 正样本抽 1-2 个确认"命中特征真做出来"；每类硬负样本各抽 1 个确认"排除特征真做出来"。
- 看图时对照设计思路的"唯一验证依据"小节逐点核。常见设计套路：
  - 实拍 vs 电子设计稿（海报贴在货架/门上、有现场环境 = 实拍；满版排版无环境 = 设计稿）
  - 抬头开错 vs 分公司内部往来（名称整体换城市/主体 = 开错；"总公司+X分公司" = 内部往来不算错）
  - 模糊脏数据（整张虚化/低分辨率，文件体积明显偏小，肉眼不可辨 → 判脏数据别硬算）
  - 纯图扫描件 vs 带文字层（见坑3）

## 坑3：设计思路的声称必须实测，不能照单全信

**现象A（纯图 PDF）**：设计思路说"scan_pdf 是纯图片型 PDF、无文字层、须 OCR"。不能靠 PDF 里有没有 BT/ET/Tj 操作符判断——ReportLab 把整图包进 Form XObject 时会留下这些操作符，但**不代表有可提取文本**。必须用 `extract_text()` 实测：返回 0 字符且页面只有 image XObject = 真·纯图扫描件。

**现象B（OCR 陷阱）**：设计思路说"ocr_text 仅参考、可能含错字、以图像为准"。要抽图核对 OCR 字段与图像内容是否**真的制造了差异**。若抽查多张都一致、没有错字 → "以图像为准"的陷阱没真正设置，考点强度低于声称。这是"瑕疵/考点偏弱"，不是"数据错误"；判定口径交用户。

**通用原则**：设计思路的每一条声称（字段、行数、纯图、错字、副本位置）都当成"待验证假设"，用工具跑一遍再下结论。实测与声称冲突，以实测为准，并在机评里写清差异。

## 坑4：Windows / PowerShell / lark-cli 工程坑

| 坑 | 表现 | 规避 |
|---|---|---|
| 内联 JSON 引号被吞 | `--filter-json '{...}'` 报 invalid JSON near byte 2 | 写进文件，用 `--filter-json @./temp_data/f.json` |
| 绝对路径被拒 | `--output d:\...` 报 unsafe output path | 用 `./temp_data/x.png` 相对路径，设 cwd 到 skill 根 |
| 脚本名遮蔽标准库 | 放 inspect.py 导致 `inspect has no attribute get_annotations` | 脚本放 scripts/ 子目录，别用标准库同名 |
| pycache 被沙箱拦 | `Not allow operate files ...__pycache__` | 跑前 `set PYTHONDONTWRITEBYTECODE=1` |
| JSON BOM | json.load 报 Unexpected UTF-8 BOM | `open(..., encoding='utf-8-sig')` |
| record-list 返回体 | 不是对象数组 | `data.data` 二维数组 + `data.field_id_list` 顺序 + `data.record_id_list` |
| record-list 无 --output | unknown flag --output | 用 `--format json` 重定向到文件 |

## 判定与机评文案规范

- 机评-2 压缩、编号分条、便于人读，只留关键结论（错在哪、真考察库在哪个副本、Gold/正负样本实测数、具体错样本编号举例），不写过程。
- "有问题"必须给出可核对的定位（副本 token、表名、字段、记录编号），不要只写"不符"。
- "无问题"机评留空；但若发现"考点偏弱/声称与实测有出入但不算错"的瑕疵，可在对话汇报里提醒用户，是否落字段由用户定。
- "未能核验"用于副本打不开/无权限，注明原因，不臆断有无问题。

## 单题核验清单（逐项打钩）

1. [ ] 解析该行指令/设计思路/考察点，列出真考察库名、规模档、新增字段、Gold数、正负样本数、唯一验证依据。
2. [ ] 逐个副本 table-list，确定真考察库在哪个副本；记录编号是否错位。
3. [ ] field-list 核新增字段存在性与类型。
4. [ ] record-list 核行数档。
5. [ ] 按分类字段统计正/负样本分布，对齐"正N+硬负M"。
6. [ ] 筛出 Gold 候选行，核数量与编号规律。
7. [ ] （多模态题）下载正/各类负样本附件，Read 看图核对唯一验证依据。
8. [ ] （扫描件题）pdf_textcheck 实测是否纯图；（OCR题）抽图核 OCR 是否设陷阱。
9. [ ] 汇总判定，写机评文案，回填两个字段，读回确认。
