# Feishu Table Evaluation Annotator

用于对照用户原始 `query` 审核飞书电子表格、多维表格及其视图、自动化等产物。核心原则是以用户意图为准、以实际配置为证据，不因“看起来像完成”而放宽，也不把合理衍生误判成冗余。

## Evaluation Stance

- 先拆 query，再看产物，避免被已有结构反向影响评测标准。
- 只把 query 明示或完成目标不可缺少的条件列为硬性约束；行业惯例、审美偏好和更优方案不是硬性要求。
- 同时检查“是否存在”和“是否可用”。有字段名、视图名或公式名，不代表配置正确。
- 以可复核证据下结论：字段类型、公式表达式、筛选条件、排序键、关联目标、实际记录或执行结果。
- 不要求产物采用评测者偏好的唯一实现；不同实现只要语义和行为满足 query，均可通过。

## Default Workflow

### 1. 建立评测对象与证据边界

读取原始 query、产物链接或截图，并识别产物类型：电子表格、多维表格，或两者组合。尽可能检查实际配置，而不只看页面展示或名称。

若产物包含多维表格仪表盘，必须执行下面的“仪表盘强制取证流程”，不能只凭 CLI/OpenAPI 返回的 dashboard 列表、`blocks: []`、组件名称或截图判定仪表盘为空、正确或错误。仪表盘组件与前端配置的主读取路径是已登录的 `ego-browser` 页面；飞书 CLI/OpenAPI 只用于 Base、表、字段和视图元数据的基线或交叉核验，不作为 dashboard 组件完整性的最终证据。

若当前无法访问产物、关键配置被隐藏或证据不足，先说明缺少什么证据并输出 `评测结果：无法评测`；不要把访问失败直接判成产物 0 分。只有已观察到明确错误时，才可对该错误判定。

#### 仪表盘强制取证流程

只要 query 或产物出现 Dashboard/仪表盘，就按以下顺序执行。Dashboard 的组件、布局、前端配置和实际渲染数据优先从 `ego-browser` 获取；第 1 步未读到组件时不得直接跳到结论：

1. **官方元数据基线**：可用飞书 CLI/OpenAPI 读取 Base、表、字段和视图元数据，记录 base token、dashboard block/table ID 及返回结构。不要用 CLI 的 dashboard `blocks` 返回判断组件是否存在。
2. **ego-browser 页面读取**：使用 `ego-browser nodejs` 复用或创建隔离任务空间，在登录态下打开与产物 URL 精确匹配的页面；读取 `pageInfo()`、`snapshotText()` 和页面 DOM。若 CLI 返回空、不完整、缺少组件，或 dashboard 对象存在但 `blocks: []`，这一步是必需的，而不是可选降级。
3. **读取前端组件状态**：先从 DOM/前端状态提取 `.layout-item.dashboard-v2`、`sheet-block-DASHBOARD`、`dashboardClientvar`、`dashboardModel` 等当前页面实际存在的组件容器或状态对象；记录每个组件的标题、类型、稳定标识、布局、表/视图 ID、图表配置和数据快照。不得读取或输出 Cookie、localStorage、sessionStorage、认证头或凭据。
4. **读取已渲染组件**：优先用 `snapshotText()` / `js()` 读取组件标题、可见数值、筛选器状态、图例、排序/排名和稳定组件标识。Canvas 图表不能因 DOM 无文本就视为无数据。
5. **确认网页请求**：检查 `performance.getEntriesByType('resource')` 或可用的 CDP 网络事件，重点识别当前页面实际出现的 `dashboard/web_ssr/charts`、`clientvars`、`block_info`、`csr/config` 等数据链路。接口路径和参数必须从当前页面资源观察结果取得，不得写死样本 token 或 ID。
6. **读取响应或声明边界**：若 ego-browser 运行时支持 CDP 网络事件，在刷新前注册只读监听并读取匹配响应 JSON；否则以 DOM、前端状态和资源清单为证据，并明确“响应体未读取”，不得臆造内部配置。
7. **最后降级**：仅当已登录页面已渲染但 DOM、前端状态、资源和响应监听仍不能取得关键证据时，才使用截图/OCR或图表悬浮提示读取可见结果。
8. **清理与保密**：浏览器操作保持只读，结束时释放接管的标签页并关闭临时任务空间；不得读取、输出或保存 Cookie、localStorage、sessionStorage、认证头和其他登录凭据。

详细执行模板、证据字段和停止条件见 [`references/dashboard-browser-evidence.md`](references/dashboard-browser-evidence.md)。

### 2. 拆解 query 为评测要点

将 query 拆成编号要点，每项包含：

- **对象/表**：需要管理哪些实体，是否要求多张表或独立清单。
- **字段**：字段语义、必填信息和必要精度；例如“几点到几点”要求时间精度，只有日期不满足。
- **关系**：对象间需要怎样关联，关联方向和目标表是否正确。
- **计算**：公式输入、计算逻辑、单位、空值和边界行为。
- **查看方式**：视图、筛选、统计、排序、分组及其具体口径。
- **仪表盘**：组件是否存在，指标、维度、聚合、数据源、筛选联动和可见结果是否满足口径。
- **自动化**：触发条件、执行动作、条件分支与执行结果。
- **样例数据**：是否必须有数据才能证明工具可用，用户是否明确要求 mock 数据。

每项标注：

- `硬性约束`：query 明示，或缺失会使核心目标无法实现。
- `验收证据`：应在产物中看到的具体配置或行为。

不要把额外内容先写进硬性约束；放到“合理衍生检查”中单独判断。

### 3. 逐层核验产物

按以下顺序检查，发现一个问题后仍继续检查，避免漏报其他独立问题：

1. **结构层**：所需表、工作表、视图、自动化是否存在；是否缺少需求项。
2. **字段层**：名称、类型、粒度、选项、默认值、必填性是否承载目标语义；多维表首列是否适合作为记录标识。
3. **关系层**：关联字段是否指向正确表、关系是否能支持所需汇总或查找。
4. **逻辑层**：公式和 lookup/rollup 等计算是否完整，引用、单位、条件、空值与边界是否正确。
5. **呈现层**：筛选、统计、排序、分组是否真的配置且口径符合 query；只有同名视图但无对应条件，视为未满足。
6. **仪表盘层**：按强制取证流程核验组件类型、指标/维度、聚合、数据源、筛选器和实际渲染值；不得只核对组件标题。
7. **执行层**：工作流触发器、条件、动作和实际执行是否正确。
8. **可验证性**：在用户要求或任务性质确需样例数据时，是否有足够 mock 数据证明关键路径。

不得仅凭字段名、视图名、公式名或工作流名推断其内部配置正确。

### 4. 判断额外内容是否合理衍生

对 query 未明示的表、字段、视图、公式或工作流逐项问：

1. 是否直接帮助完成、浏览、维护或验证用户目标？
2. 是否不改变用户要求的业务口径？
3. 是否没有制造明显重复、冲突或额外操作负担？
4. 是否不会让核心信息更难找到或使用？

四项均成立，记为 `合理衍生`，不扣分。若额外内容无助于目标、与已有内容重复、引入冲突口径或显著增加负担，记为问题并使用 `冗余产物`；若它同时造成其他具体错误，可追加相应标签。

### 5. 给出二分结果与归因

- `评测结果：1`：全部硬性约束均满足，关键配置和行为正确；允许存在合理衍生。
- `评测结果：0`：至少一个硬性约束未满足，或存在会实质影响正确性、可用性的配置/逻辑错误。
- `评测结果：无法评测`：关键产物或配置不可访问，且现有证据不足以判 0 或 1。

结果为 0 时，列出所有已确认且互相独立的错误。每条错误必须包含：对应要点、观察到的配置、为何不满足、归因标签。只使用 [`references/attribution-labels.md`](references/attribution-labels.md) 中的标签；一条问题可有多个标签，但只选直接原因，不堆砌近义标签。

## Important Gotchas

- 日期字段不等于日期时间字段；query 要求具体时刻或时段时，精度必须到时间。
- 创建了“按日期筛选”等命名视图，但未配置筛选条件，仍是失败。
- 能手工筛选不等于已交付用户明确要求的预设查看方式。
- 公式能返回值不等于逻辑正确；必须核对引用、条件、单位和边界。
- 多维表首列承担记录标识作用；若首列是不可辨识、易重复或语义错位的字段，单独检查 `首列定义不合理`。
- 缺 mock 数据只有在用户明确要求，或没有数据就无法验证关键交互/计算时才是错误；不要机械要求每个产物都有 mock 数据。
- 美化、说明字段、辅助视图和便捷汇总通常可视为合理衍生，只要不冲突、不喧宾夺主。
- 不因命名与 query 不完全一致就判错，应检查其语义和实际行为。
- CLI/OpenAPI 的 dashboard `blocks: []` 只表示公开读取未返回组件，不等于网页端仪表盘为空；含 dashboard 的评测必须走 `ego-browser` 的 DOM、前端状态和页面资源读取路径。
- 网页端 Dashboard V2 可能由 DOM 统计卡、排名列表和 Canvas 图表混合渲染；必须组合 DOM、页面资源、响应数据或截图证据。
- 私有网页接口依赖登录态且可能变化；评测应记录观察到的路径和证据，不把私有接口形状当成永久公开契约。

## Output Format

严格按下列结构输出；没有错误时省略“错误原因”和“归因标签”。

```text
评测要点：
1. [硬性约束] {从 query 拆出的要求}
   验收证据：{应检查的字段/配置/行为}
2. ...

合理衍生检查：
- {额外内容}：合理衍生 / 不合理；{一句理由}
- 无额外内容（如适用）

评测结果：1 / 0 / 无法评测

错误原因：
1. 对应要点 {编号}：{观察到的事实}；{不满足 query 的原因}。归因：{标签}
2. ...

归因标签：{标签1}、{标签2}
```

若结果为 `无法评测`，在结果后补充：

```text
缺失证据：{无法访问的产物或必须查看的配置}
```

## Completion Check

输出前确认：

- query 中每个显性要求都映射到了评测要点。
- 每个 0 分原因都有产物证据，不是主观偏好。
- 字段、公式、筛选/统计、排序/分组、关联和工作流已按适用范围核验。
- 产物含仪表盘时，已完成“CLI/OpenAPI 元数据基线 -> ego-browser 页面 DOM/前端状态/资源 -> 响应监听（可用时） -> 截图/OCR”的取证链，并记录证据边界。
- 额外内容已单独做合理衍生判断。
- 结果、错误原因和归因标签互相一致。
