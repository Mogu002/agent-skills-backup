# 数据接地与可用性判定（grounding）

答案只能来自目标 Base 的真实数据与附件内容。本文件给出"如何判断数据能否支撑 query"的方法论。

## 第一步：真实 schema vs 设计思路

拿到副本 Base 后，先对比 `+field-list`/`+table-list` 的真实结构与【样张设计思路】描述：

- 行数：设计常写 >100/120 行，真实可能只有 60 行。
- 字段名：设计用英文代号（report_id/revenue/risk_text），真实可能是中文业务字段（公司名称/股票代码/报告类型/财报文件）。
- 主体：设计举例（如"宁德时代"、文号"国发〔2022〕9号"），真实可能是随机抓取的其它主体。

**结论优先级：真实数据 > 设计思路。** 差异要在参考答案的【数据与设计差异】段落如实点明。

## 第二步：区分"真实爬取数据"与"按考点构造的合成样张"

同一张表里常混有两类记录：

1. **通用爬取/填充数据**：主体零散、与 query 考点无必然关系（如"政府工作报告""人大常委会公报""价格监测周报"等）。
2. **按本题考点专门构造的合成样张**：是真正的正负样本集合，特征：
   - 文件名/编号带前缀：`-pos-`（正样本）、`-neg-`（硬负样本）、`-fill-`（填充）；或文号段（如"市改规划"=正、"市改经"=硬负、"办发"=填充）。
   - 内容页脚常标注"合成评测样张/评测沙盒·虚构样本，不代表真实披露或官方文件"。
   - 正样本之间构成可对齐的跨表关系；硬负样本故意制造"看似匹配实则口径/主体不符"。

**只有合成正样本（pos）才是 query 的真正命中集合**；neg/fill 不计入。若全表都是通用爬取数据、无 pos 构造，则该题很可能"真实数据无法支撑 query"，应如实少报。

## 第三步：跨表语义 Join 的口径纪律

query 常用三种语义键，匹配时都要卡"口径/有效性"：

- **公司全称**：精确同名才算命中；"同名不同文件类型"要看 query 要的是哪种（如 query 要"招股书"，而该公司在 IPO 库是"可研报告"，不算命中）。子串近似匹配要显式标注为推断。
- **行业主题**：政策公文必须**点名具体赛道**才能与研报赛道/财报行业对齐；"产业扶持/城市管理/营商环境"等泛行政主题无法构成行业桥，不能强行挂钩。
- **指标口径**：指标同名但统计口径不同 = 硬负样本。例：政策"年初至今累计同比" vs 统计"当月同比"；政策"五年累计降幅" vs 统计"当年同比降幅"。PDF 若明示"不可直接比对"则排除；明示"与政策文件考核口径一致"且数值一致才计入正样本。

## 第四步：PDF/图片真实读取

- query 要求"打开 PDF 封面/正文核对"时，必须真正读内容，不能只凭结构化字段或文件名推断。
- 真实 PDF（有文字层）：用 `scripts/pdf_text.py` 抽文本，核对封面公司全称、正文量化目标段、评级页等锚点。
- 扫描件/图片/无文字层 PDF：走视觉或 OCR。
- **伪扫描件识别**：PDF 自称"扫描件"但实为程序生成（Producer=ReportLab，内容流含 BT/ET 文本块与 /Font 字体对象）→ 有完整可提取文字层，可直接抽文本，不必依赖视觉 OCR。此时若题目考点是"OCR 不可靠时读图像像素"，考点被弱化，应在差异说明中指出。
