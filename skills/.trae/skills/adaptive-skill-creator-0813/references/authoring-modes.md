# Authoring Modes

在 Skill Fit Gate 通过后读取本文件。先选主模式，再决定是否叠加 Harden。

## 1. Evidence Inventory

不要只问“材料多不多”。分别记录：

| 证据 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| 文档、SOP、政策 | 声明的流程和约束 | 流程真实有效、仍未过期 |
| 代码、schema、配置 | 当前实现和机器契约 | 用户意图、异常处理是否合理 |
| 成功轨迹 | 某条路径至少成功过 | 可泛化性和失败边界 |
| 失败轨迹、review 纠偏 | 薄弱环节和 gotchas | 修复方案一定普适 |
| 模板、黄金输出 | 期望结构和质量 | 生成过程和事实正确性 |
| 验证器、测试、回读 | 可观察的完成信号 | 未覆盖属性的正确性 |

优先使用多种证据交叉支持。发现材料互相矛盾时，保留差异并寻找执行证据，不擅自选一个看起来更正式的版本。

## 2. Explore Mode

适用：只有想法、一次性成功案例、未经执行的草稿，或没有可靠验证器。

目标：产出最小可测试假设，不伪装成成熟实践。

步骤：

1. 收窄为一个代表性用户结果。
2. 写最小 `name`、`description`、默认策略和停止条件。
3. 只加入当前证据能支持的约束；把推测标为待验证。
4. 默认只建 `SKILL.md`。只有现成材料太长或已有确定性脚本时才增加 support files。
5. 用正例、负例和一个代表任务做 dry-run。
6. 收集真实使用中的触发、追问、失败和修正，准备进入 Codify 或 Learn。

不要把模型的常识复述、臆造 SOP 或预建目录当作进展。

## 3. Codify Mode

适用：有可靠材料、稳定术语或重复执行过的 SOP，能够说明默认流程和边界。

目标：把现有实践压缩为 Agent 能发现和执行的工作流。

步骤：

1. 读取现有材料和相关执行记录，确认版本、权威性和冲突。
2. 提取模型不能安全推断的内容：顺序、默认值、组织规则、异常、禁止项和验证方式。
3. 用一个内聚结果定义 Skill 边界；不同触发目标、工具或成功标准才拆分。
4. 写默认策略，而不是罗列材料中的所有可选做法。
5. 把长规范、schema、例外表和示例按读取条件放入 references。
6. 用真实任务回放，比较有 Skill 和无 Skill 的差异。

材料很多但从未执行时，保持 Explore 的谨慎措辞；不要把文档权威性等同于行为证据。

## 4. Learn Mode

适用：有多条成功/失败轨迹、人工纠偏和可用验证信号。

目标：让 LLM 归纳候选模式，由验证器或专家决定是否沉淀。

步骤：

1. 将轨迹分为归纳集和保留集，避免在同一批案例上总结又验收。
2. 定位错误发生在路由、判断、工具、执行、验证还是输出层。
3. 让 LLM 归纳最小候选规则，要求每条规则指向证据和预期改善。
4. 合并重复规则，删除仅解释单个案例的故事。
5. 在保留集上对比无 Skill、旧 Skill 和候选 Skill。
6. 只保留稳定改善成功率、风险或成本的规则；记录仍有分歧的场景。

自生成内容只是候选压缩，不是新证据。没有外部信息或验证时，模型重述自己的先验通常不会创造可靠专长。

## 5. Harden Overlay

满足任一条件时考虑加固：

- 外部写入、删除、发布、转账、授权或生产变更
- 输出必须符合严格 schema、计数或顺序
- 错误难以恢复、影响他人、涉及隐私或合规
- 高频执行使小概率错误累积为显著风险
- 误触发昂贵，或与相邻 Skills 高度相似

按需增加：

- 参数和前置条件校验
- 非交互、可测试、幂等脚本
- dry-run、preview、diff、回滚或恢复路径
- 独立验证器和执行后回读
- 最小权限、显式确认、审批和审计日志
- hook、CI、policy 或状态机中的强制检查

不要仅用更强硬的自然语言替代系统控制。LLM 可能因长上下文、压缩、工具结果或模型差异跳过软约束。

## 6. Five-Layer Design

只实现对当前任务有用的层，不要求每层单独建文件。

### Discovery

定义 `description`、应触发例、负例、hard negative 和相邻 Skill 边界。

推荐结构：

```text
可观察能力/结果 + Use when/用户场景 + 高区分度表达 + 必要排除项
```

不要在 description 中塞工作流、来源故事或平台实现细节。

### Reasoning

写清：

- 目标和最小必要输入
- 默认选择及理由
- 改走其他路径的观察信号
- 可安全推断与必须询问的内容
- 不支持、停止或升级条件
- 真实 gotchas 和质量标准

### Execution

对模糊、情境化任务提供原则与决策条件；对脆弱、重复、严格任务提供脚本或精确契约。

脚本至少说明：执行还是阅读、输入、输出、退出码、依赖和副作用。需要重试时优先幂等；有写操作时优先 dry-run。

### Verification

定义独立完成证据，例如测试、schema 校验、渲染、API 回读、文件 diff 或专家 rubric。不要让生成答案的同一段自然语言成为唯一验收者。

### Lifecycle

团队或生产级 Skill 按需记录：来源、兼容平台、版本、owner、评测集、回归条件和弃用方案。个人低风险 Skill 不必为此搭脚手架。

## 7. Information Architecture

优化信息价值，不机械优化文件长度：

- 主文件保留高频决策、默认策略、关键护栏和资源入口
- references 承载只在特定条件下需要的长材料
- scripts 承载确定性、重复和低容错操作
- assets 承载最终交付直接使用的模板或静态资源
- evals 只在案例会持续回归或已形成代表分布时创建

优先让主文件直接指向目标资源。若资源规模大、分类稳定且直接 fan-out 会增加选择成本，可以使用一个清晰索引；索引必须告诉 Agent 按什么条件选择下一份资料。

## 8. Portable Core and Adapters

核心工作流使用最少的平台假设。平台专属工具、路径、frontmatter 或权限机制满足以下条件时才加入：

- 能显著提高可靠性或能力
- 有清晰触发条件
- 不冒充跨平台默认行为
- 有无该平台时的行为已说明

不要为了最低公分母牺牲必要的平台能力，也不要把一次调试环境写成通用前提。
