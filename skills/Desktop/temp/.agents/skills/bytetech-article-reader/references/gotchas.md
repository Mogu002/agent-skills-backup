# Gotchas

本文件沉淀 ByteTech 文章读取过程中暴露出的高频坑点，重点是“外层壳”和“真实正文入口”不要混淆。

## 1. `curl` 成功不代表文章可读

ByteTech 链接可能返回 200，但内容其实是飞书授权页或登录壳子。先看标题、正文和关键脚本，不要只看 HTTP 成功。

## 2. 锚点里的 doc token 不一定可直拉

像 `#doxcn...` 这样的锚点看起来像飞书文档 token，但未必能被 `lark-cli docs +fetch` 稳定拉取。它可能只是站点内部映射的一部分。

## 3. 真正可用的 token 可能藏在内嵌 Feishu iframe 里

ByteTech 外层文章页可能只是一个壳，正文实际来自内嵌的 Feishu `docx` 页面。要找的是这类真实 token，而不是盯着站点锚点不放。

## 4. Chrome 会话是资产

如果用户已经在 Chrome 里打开了目标文章，这通常比重新访问 URL 更可靠：

- 登录态已经就绪
- 页面可能已经滚到关键段落
- 站点的前端 hydration 已经完成

## 5. 一旦拿到真实 token，就别继续在页面里硬抠正文

如果已经拿到了真实 Feishu doc token，默认应该立刻切到 `lark-cli docs +fetch`。继续在 ByteTech 页面里用 DOM、截图或手工复制正文，只会增加噪声。

## 6. DOM 不是唯一真相

页面的可见正文可能存在，但全量 `innerText` 会混入：

- 右侧作者信息
- 树形目录
- 推荐文章
- 底部专题列表

因此应把截图与局部抽取结合起来，而不是单吃一个大文本串。

## 7. 目标可以升级成“拿整篇干净正文”

在还没找到真实 token 时，目标可以是“够用提炼”；但一旦确认正文本体就在 Feishu doc 里，目标就应该升级成“直接拉整篇干净 markdown 正文”。
