# Doubao Base 评测规则

本文件是内部参考文档主文的可执行摘要，快照日期为 2026-09-14。评论区讨论没有写入规则；若主文更新，应重新提取并回归计分测试。

## 1. 题型与权重

题型只保留三类。原多轮题统一归为创建类，只检查最终产物是否满足合并后的全流程需求。

| 题型 | 维度 | 权重 |
|---|---|---:|
| 创建类 | 数据表设计 | 35% |
| 创建类 | 数据合理性 | 20% |
| 创建类 | 配置正确 | 35% |
| 创建类 | 产物丰富度 | 10% |
| 编辑类 | 数据表设计 | 40% |
| 编辑类 | 数据合理性 | 20% |
| 编辑类 | 配置正确 | 40% |
| 数据分析 | 指令遵从 | 100% |

维度含义：

- **数据表设计**：在记录为空时，Table 表头、字段类型、关系和公式设计是否正确。
- **数据合理性**：Table 内记录是否正确，mock 数据是否缺失或明显反常识。
- **配置正确**：Table 以外及 Table 的视图配置等能力是否正确，包括 Workflow、Dashboard、Permission、Form、筛选、分组和视图。
- **产物丰富度**：AI 生成的页面级产物类型是否足够丰富。
- **指令遵从**：数据分析结果是否与 Query 要求一致。

## 2. 通用判分规则

1. 子维度使用 0/1 二元评分；任一适用二级子维度为 0，对应一级维度直接为 0。
2. `/` 表示该题结构性不考察该维度。只对适用维度加权，并按适用权重和重归一化：

   `单题分 = Σ(适用维度权重 × 维度分) ÷ Σ(适用维度权重)`

3. 用户明确要求的非表结构功能缺失只在“配置正确”的对应能力子域扣分，避免同一根因重复扣分；不要因同一缺失再判产物丰富度为 0。Table 页面级缺失按“数据表设计”的明确条款判 0，也不再重复归入配置正确。
4. `/` 不是“没看到”“没权限”或“没检查”。这些情况应标记待核验，并暂停总分。
5. 批次示例采用每题归一化得分的算术平均；保留每题独立分数后再聚合。

示例：创建类评分为 `数据表设计=0、数据合理性=/、配置正确=1、产物丰富度=0`，则适用权重和为 `0.35+0.35+0.10=0.80`，单题分为 `0.35/0.80=0.4375`，两位小数显示为 `0.44`。

## 3. 数据表设计

命中任一适用错误即为 0：

- 字段类型违反常识或业务语义，例如金额使用文本字段。
- 公式逻辑错误，或字段格式与公式结果冲突；除数为 0 的情形豁免。
- 复选框判断使用 `=true` 而不是 `=1`。
- 关联字段或查找引用指向错误。
- AI 字段配置错误。
- 缺少必要的索引列。
- 字段命名混乱，无法识别业务含义。
- Table 页面级产物缺失。
- 字段设计不符合原始 Query。

全部适用检查均通过时为 1：字段类型契合业务，公式逻辑正确，关联与查找引用正确，AI 字段配置合理，命名规范，并有清晰索引列。

## 4. 数据合理性

### 用户未提供数据

命中任一情况即为 0：

- 半数以上记录没有 mock。
- 前面的空记录未 mock，后续记录已 mock，造成排序失真。
- 单表 mock 记录少于 5 条。
- 涉及动态时间但没有按当前时间递推。
- mock 数据违反常识，例如订单日期晚于发货日期。
- 字段值明显生造，与业务脱节。

全部适用检查通过时为 1：mock 充分，单表至少 5 条，动态时间递推合理，数值和逻辑符合常识。

### 用户提供数据

任意一处具体记录与用户输入不符即为 0；只有已核对的适用记录均一致时才为 1。

## 5. 配置正确

先列出 Query 要求或产物实际包含的适用子域。任一适用子域为 0，则整个“配置正确”为 0；没有适用证据的子域不能自动写 1。

### 5.1 Workflow

命中任一情况即为 0：

- 配置错误导致工作流无法保存，包括爆红、必填为空或不完整、多分支结构异常、前端渲染异常、服务异常、数据损坏或配置面板空白。
- 触发器、逻辑、处理节点或参数与 Query 不符。
- 循环内加入判断节点。

全部触发器、逻辑节点、处理节点和参数均符合 Query，能够启用、运行并达成需求时为 1。以下主文列明的情形可豁免：

- “创建飞书日程”节点仅“选择日历”为空。
- 群授权失败时使用提出人兜底。
- Query 中的离职人员替换为在职人员姓名后重跑。

### 5.2 Dashboard

命中任一情况即为 0：

- 指令误解或遗漏。
- 筛选错误或字段配置错误。
- 组件显示异常。
- 排版违规。
- 任务未完成。

全部要求准确执行，且布局符合 F/Z 阅读顺序时为 1：指标卡或切片器 → 趋势图表 → 详细表格或透视表。整体保持紧密、左对齐；每个模块末尾可留空白。满屏均为同类组件并严重影响阅读，或组件缩放异常时为 0。

### 5.3 Permission

命中任一情况即为 0：

- 必要角色缺失、凭空新增未要求角色，或 Query 要求新建角色却修改同名已有角色。
- 一级权限（数据表整体）与 Query 不一致。
- 二级权限出现至少 1 处扩权。
- 二级权限缩权超过 1 处。
- 配置可编辑记录范围但未说明可阅读范围时，开放全表可阅读，造成扩权。
- 违反系统字段或自动字段的权限约束。
- 筛选条件跨表推导、右值为二级推导，或使用不支持的字段类型。
- Query 出现“只能”“仅可”等排他表达，但同层级没有排他。
- Query 明确“可管理”但未授予管理权限。
- App 场景未提页面权限时，没有采用“所有页面可阅读、所有按钮可见”的默认配置。

角色齐全且名称对应、一级权限完全符合 Query、二级扩权为 0，且二级缩权不超过 1 处并只落在 Query 未明确的字段或权限项上时为 1。

### 5.4 Form

命中任一情况即为 0：

- 题型选错。
- 必填或选项设置错误。
- “其他”选项不在最后。
- 题干与选项脱节。
- 空壳题，没有实际内容。
- 选项逻辑混乱。
- 题目序号混乱。
- 题目顺序不符合填写逻辑。

题型、必填、选项、全局设置和外观设置均符合 Query 时为 1。

### 5.5 Table 配置

筛选条件、分组排序、视图配置、动态数据表设置或单值/多值判断任一错误即为 0；全部适用配置正确时为 1。字段类型、公式、关联和索引列归入“数据表设计”，不要重复扣分。

## 6. 产物丰富度

- **先判断是否适用。** 创建类 Query 若明确限定或完整列举了应创建的页面级产物类型，则本维度不再按类型数量评分，内部记为 `NA_QUERY`，人评标签写“不涉及（query要求）”。这适用于任意明确的产物类型组合，不限于只要求 Table，或 Table 加另一种页面。
- “明确产物类型”要求 Query 给出了可视为完整交付范围的类型清单，例如只建数据表、建数据表和表单、或明确列出 Table/Form/Workflow/Dashboard 等组合。只描述业务目标、功能效果，或使用“至少包含”“例如”“等”这类开放表述时，不视为已经限定完整类型范围。
- `NA_QUERY` 由 Query 的明确范围决定，不用于掩盖缺失或错误。明确要求的类型缺失时，仍在“数据表设计”或“配置正确”的对应能力域判 0；产物丰富度继续记 `NA_QUERY`，避免同一缺失重复扣分。出现额外的未要求类型也不把本维度改判为 1；若 Query 明确禁止额外页面，则把违背该限制的事实归入对应实质维度，不在丰富度重复扣分。
- 只有创建类且 Query 没有明确限定页面级产物类型时，才按丰富度评分：
  - 0：只有 Table，或只有 Table 加另一种页面级产物。
  - 1：Base 中包含 Table 在内至少 3 种页面级产物。
- 编辑类、数据分析类及其他非创建类题型统一为普通 `/`，人评标签写“不涉及”，不能使用“不涉及（query要求）”。

页面级产物可包括 Table、视图、Form、Permission、Workflow、Dashboard 等。若用户明确要求的某个产物缺失已经归入对应能力维度，不能把同一缺失作为丰富度为 0 的唯一原因；丰富度为 0 需有独立的类型数量事实。

## 7. 数据分析

数据分析类只使用“指令遵从”一个维度，权重 100%。结果完全符合 Query 的对象、口径、范围和输出要求时为 1；存在已确认的误解、遗漏或不一致时为 0。来源主文没有给出更细的分析质量子规则，不要自行增加隐性扣分项。

## 8. 解释边界

- 编辑类沿用数据表设计、数据合理性和配置正确的对应细则；只检查本题适用部分，并按 40%/20%/40% 计分。来源主文未给出编辑类独立例外。
- 批次算术平均由来源中的四题示例反推；若具体评测批次另有聚合协议，以该协议为准并明确说明差异。
- 来源只说明 `/` 是结构性不适用，没有给出逐题型的完整适用清单。若某一级维度的全部子项均为 `/`，计分脚本把该一级维度解析为 `/`；这是实现假设，必须保留结构性理由。
- `NA_QUERY` 是对创建类产物丰富度不适用原因的保真编码，计分上与 `/` 相同，均从适用权重分母中剔除；输出时必须保留为“不涉及（query要求）”，不能降级成普通“不涉及”。
- “功能缺失不重复扣分”用于根因归一，不用于掩盖另一个独立错误。相同对象上不同事实错误仍可分别记录，但同一事实只能有一个主要计分归因。
- 无法取得完整配置时，输出待核验而不是把“未观察到”当成“不存在”。
- “前空后有”、动态时间容差、时区、空格子和修改既有数据的边界未在主文定义；不要自行发明阈值。
- Workflow 的通过描述要求能够启用、运行并满足需求；只有“可保存”证据时仍需补足启用或运行证据，不把评论区追问写成新规则。
- Dashboard 只使用主文给出的紧密布局、F/Z 顺序和左对齐要求，不推导像素级算法。
- Permission 的一级/二级与扩权/缩权判断必须落到实际角色和配置证据；主文没有定义跨角色聚合规则时，不自行补齐。
