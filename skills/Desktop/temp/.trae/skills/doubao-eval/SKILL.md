# Doubao-Eval

按照用户视角评测豆包生成、编辑或分析的飞书 Base 产物。评测对象是原始 Query 与最终可用产物；名称、Spec、过程描述或“已创建”提示都不能替代实际配置证据。

## Default Policy

- 这是只读评测 Skill，不创建、修改、修复或重跑产物。用户同时要求修复时，先完成评测；任何写操作都按对应工具的授权边界另行执行。
- 每次评测都读取 [references/rubric.md](references/rubric.md)。只把该文件标明的规则作为评分依据，不用来源文档评论区、个人偏好或行业惯例新增扣分项。
- 最终产物包含飞书 Base URL 时，必须先使用 `$lark-base-reader` 做 URL 定位和读取路径分流；它是入口与路由层，不替代后续的结构化读取或浏览器取证。
- 必须有原始 Query 和可复核的最终产物证据。访问失败、权限不足、配置未展开或截图看不清属于证据不足，不是 0 分，也不能写成 `/`。
- 只有观察到明确错误才判 0；判 1 需要覆盖该维度全部适用检查点。发现一个错误后仍检查其余适用维度，避免漏报独立问题。

## Required Inputs

至少取得：

1. 原始 Query；多轮任务需取得合并后的全流程要求。
2. 最终产物或足以复核配置的证据，例如 Base 链接、结构化导出、完整配置截图或执行结果。
3. 题型；若用户未指定，按以下规则判断：
   - 从零生成产物，或来源规则中的原多轮题：`创建类`。
   - 在既有产物上完成变更：`编辑类`。
   - 主要交付是基于数据回答问题或给出分析：`数据分析`。

题型仍有歧义时必须先询问，因为题型会改变维度和权重。不要让计分脚本代替题型判断。

## Workflow

1. **拆 Query。** 列出显性要求、预期对象、关键配置或行为、所属能力域和验收证据。创建类还要判断 Query 是否已经明确限定或完整列举应创建的页面级产物类型；合理衍生不自动扣分。
2. **定位并规划取证。** 产物是 Base URL 时先按下方“Base 产物读取入口与分流”执行；其他证据则直接判断其覆盖范围。优先读取结构化配置和真实页面；字段、公式、关联、筛选、工作流、权限等内部配置不能仅凭对象名称推断。涉及视觉布局时补页面证据。保持只读，除非用户另行授权有外部效果的测试。
3. **确认完整性。** 对每个拟判 0 的结论检查证据是否直接、完整并覆盖目标配置。若不能确认，标记 `待核验`，不得猜测。
4. **逐维度判定。** 按 [references/rubric.md](references/rubric.md) 给出 0、1 或 `/`。创建类的 Query 若已明确限定交付的页面级产物类型，则“产物丰富度”使用 `NA_QUERY`，人评标签为“不涉及（query要求）”；该规则适用于任意明确产物类型组合，不限于只建 Table 或 Table 加一种页面。创建类和编辑类都必须显式填写 Workflow、Dashboard、Permission、Form、Table 五个配置子域，实际不涉及的子域写 `/`。任一适用子域为 0，则“配置正确”一级维度为 0。
5. **去重归因。** 同一根因只归入一个主要维度。用户明确要求的非表结构功能缺失归入“配置正确”的对应能力子域；Table 页面级缺失归入“数据表设计”。不要再把同一缺失作为产物丰富度或其他维度的唯一 0 分理由。
6. **确定性计分。** 语义评分完成后执行 [scripts/calculate_score.py](scripts/calculate_score.py)；把链接解析为本 Skill 目录下的实际路径，再运行 `python3 <skill-path>/scripts/calculate_score.py <ratings.json> --pretty`。输入契约和示例见脚本头部。脚本只计算，不判断事实是否正确。
7. **输出结论。** 已评分时先输出与人评表同名、同顺序的扁平字段，再给题型、证据边界、维度表、公式、全部已确认问题和待核验项。优先直接使用计分脚本返回的 `human_eval_fields`，不要手工改字段名或状态文案。

## Base 产物读取入口与分流

只要最终产物证据中包含飞书 `/base/` URL，就必须先读取并执行 `$lark-base-reader`，按其 `references/cli-reading-paths.md` 定位后再下钻：

1. 先用 `+url-resolve --as user` 取得 `base_token`、当前对象 ID 和对象类型；不能仅从 URL 参数猜对象类型。
2. 创建类、全库核验、范围未知，或需要判断“产物丰富度”时，继续用 `+base-block-list --as user` 读取完整左侧栏对象清单。单对象编辑题可在定位后只检查目标对象，不为“完整”扩读全库。
3. 按对象与证据类型分流：
   - 表字段、记录、视图、Workflow 或其他可结构化配置：转 `$lark-base` 的相应只读分支。
   - Form、Permission、Dashboard 真实渲染，或 CLI 信息不全的页面证据：转 `$ego-browser`，使用已登录页面只读取证。
   - 遇到 `token_missing`、`need_user_authorization`、`missing_scopes` 或 `verify_failed`：停止 Base 读取并转 `$lark-shared` 恢复认证。
4. `+url-resolve` 只表示入口对象已定位，不代表整个 Base 已检查；`+base-block-list` 也只能证明对象存在，不能替代配置细节或真实页面证据。

## Scoring Invariants

- 顶层维度只允许 `0`、`1`、`/`；仅创建类的 `artifact_richness` 额外允许 `NA_QUERY`。`/` 仅表示普通结构性不适用，`NA_QUERY` 仅表示 Query 已明确限定页面级产物类型；未知、未检查或证据缺失不能写成任一种不适用。
- 创建类和编辑类的 `configuration_correctness` 必须是且只能是 `workflow`、`dashboard`、`permission`、`form`、`table` 五个子域的完整对象；缺键或未知键都阻止正式计分，不能自动补成 `/`。
- 任一适用二级检查为 0，对应顶层维度直接为 0；不计算二级小分。
- 单题分数只在适用维度上重归一化：

  `Σ(适用维度权重 × 维度分) ÷ Σ(适用维度权重)`

- 批次总分默认对每道题的归一化单题分做算术平均。不要把所有维度跨题直接池化。
- 保留未舍入值用于计算；展示单题分时可保留两位小数，同时给出精确算式。需要整数百分制时使用四舍五入，并同时保留精确百分比。
- 任一必需维度仍为待核验时，不输出推测总分；状态写 `待核验` 并列出缺失证据。

## Output Contract

评分完成后，默认先输出以下人评格式化字段。字段名和顺序必须保持不变：

```text
数据表设计：有问题 / 无问题 / 不涉及
数据合理性：有问题 / 无问题 / 不涉及
Workflow配置：有问题 / 无问题 / 不涉及
Dashboard 配置：有问题 / 无问题 / 不涉及
Permission配置：有问题 / 无问题 / 不涉及
Form 配置正确：有问题 / 无问题 / 不涉及
Table 配置正确：有问题 / 无问题 / 不涉及
指令遵从【数据分析专有】：有问题 / 无问题 / 不涉及
产物丰富度【创建类题目专有】：有问题 / 无问题 / 不涉及 / 不涉及（query要求）
最终分数：{0 到 1 的精确值}
```

转换规则固定为：内部评分 `0 → 有问题`、`1 → 无问题`、`/` 或脚本中的 `NA → 不涉及`；仅创建类产物丰富度的 `NA_QUERY → 不涉及（query要求）`。五个配置字段来自 `configuration_correctness` 的同名子域；该一级维度只参与折叠和计分，不另设人评输出字段。编辑类及数据分析类的产物丰富度、非数据分析题的指令遵从，以及题目结构上不考察的其他字段都写普通“不涉及”。

紧接着输出可复核说明：

```text
评测标准：Doubao Eval
评测状态：已评分
题型：创建类 / 编辑类 / 数据分析

Query 要点：
1. {要求}；验收证据：{证据}

维度评分：
| 维度 | 权重 | 二级/子域结果 | 一级评分 | 决定性证据 |
| ... |

计分：{适用维度加权和} ÷ {适用权重和} = {结果}

问题明细：
1. {对象/配置}：预期 {…}；实际 {…}；主归因维度 {…}。

待核验：
- {缺失证据及其影响；没有则写“无”}
```

没有已确认问题时省略“问题明细”。批量评测时每题都保留一组人评格式化字段和最小证据，再给出题目等权均分；不能只报一个总数。

若任一必需评分仍待核验，不生成可回填的人评字段值，也不填写“最终分数”；改为输出 `评测状态：待核验`、当前已确认事实和缺失证据。不得用“不涉及”掩盖未检查、无权限或页面不可见。

## Routing Boundaries

- 明确要求豆包三题型加权规则、维度打分或该规则下的批量标注：使用本 Skill。
- 只要求普通 Building/Decision 产物整体 0/1 与 Spec 归因：使用相应 Building 评测 Skill。
- 只要求 BWE-Direct/Reflect 仪表盘评测：使用 Dashboard 评测 Skill。
- 只要求 App Building 2.0 验收：使用 App Building 评测 Skill。
- 只要求通用表格/Base 是否满足 Query，未指定豆包权重口径：使用通用表格或 Base 评测 Skill。
- 要创建、编辑或修复 Base：使用构建类 Skill；不要用本 Skill 代替实施。
- 同时指定本标准与另一套标准时，分别评分并标明标准名；禁止混合权重，也不要把 Dashboard BWE 的 `-1` 或其他标准的标签带入本标准。

## Stop Conditions

- 缺少会改变题型或评分的 Query 信息：询问用户。
- 关键产物不可访问且没有等价证据：输出 `待核验`，不判 0/1。
- 验证需要提交记录、触发通知、改权限或运行生产工作流：没有用户明确授权就停止在配置检查。
- 来源规则出现冲突或已更新：保留冲突，不擅自选择；请求规则 owner 或用户确认后再评分。

## Maintenance

- 评分细则以 [references/rubric.md](references/rubric.md) 为唯一完整版本；规则改变输入 token、计分或人评输出时，只在主文件保留必要契约，并同步修改脚本与测试，不复制整段细则。
- 修改权重或计分规则后，在 Skill 根目录运行 `python3 -m unittest discover -s tests -v`。
- 路由变化时用 [evals/routing-cases.json](evals/routing-cases.json) 回归正例、负例、hard negatives 和多意图场景。
