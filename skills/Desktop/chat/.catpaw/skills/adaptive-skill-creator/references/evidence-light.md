# Evidence-Light Workflow

这是 `adaptive-skill-creator` 的低证据参考路径，不是一个可独立触发的 skill。
当用户只有一个想法、缺少现成材料，或当前更重要的是先搭出最小可用骨架时，读取本文件。

## 适用前提

在以下情况走这条路径：
- 用户没有提供稳定文档、SOP、代码、schema 或历史案例
- 当前任务更像从 0 到 1 搭出一个可用 skill，而不是沉淀成熟实践
- 你无法证明某个 workflow 已经被反复验证过

这条路径的目标不是一次写满，而是先产出最小可用、可继续迭代的 skill。
只保留当前任务真正需要的结构、默认路径和收敛方法。

如果后续出现稳定材料、真实失败案例、既有 `SKILL.md` 或重复执行过的流程，应切换到 `references/evidence-rich.md`。

## 前置 gotchas

先避免这些常见错误：
- 不要把缺失的项目知识臆造成“最佳实践”
- 不要为了显得完整，预先创建一堆 `references/`、`scripts/` 或 `assets/`
- 不要把教程式背景知识塞进 `SKILL.md` 主文件
- 不要一次追问很多问题；只问会阻塞默认路径的关键信息
- 不要把第一次写出的 `description` 当成已经验证稳定的触发描述
- 不要给很多平级方案；先给一个保守、明确、可执行的默认方案
- 在编写或修改 `SKILL.md` 时，必须严格区分“用户输入”“agent 内部中间产物”“最终输出字段”三类对象。凡是内部推导得到的内容，必须显式标注为“候选/草稿/内部生成”，不得直接用最终输出字段名或用户输入字段名来描述内部步骤；否则会让人误以为该内容需要由用户先提供。

## 默认立场

- 先产出最小可用版本，再根据真实使用迭代
- 默认采用最小结构；若不能证明 support files 有用，就先不要创建
- `description` 优先覆盖用户真实说法和触发场景，而不是内部设计术语
- 如果范围拿不准，先缩小 skill 边界，不要一开始写得很大
- 如果信息不足以支撑“高质量沉淀”，就写得更克制

## 最小交付目标

低证据路径下，默认交付物应满足：
- 一个合法的 `name`
- 一个围绕用户意图编写的 `description`
- 一个保持轻量的 `SKILL.md`
- 零个或一个有明确用途的 support file
- 至少能支撑一个代表性请求，而不依赖隐藏上下文

如果当前信息还不够，不要硬造复杂结构；先把默认路径写清楚。

## 默认工作流

按以下顺序执行：

1. 收窄任务边界
   - 判断用户是要新建 skill、整理已有草稿，还是先搭一个最小骨架
   - 若缺少关键信息，只补问最少的问题；优先询问会影响 `name`、`description` 或默认路径的内容

2. 先写触发面，再写正文
   - 先确定 skill 名称
   - 再根据用户原话、典型请求和目标产出，起草 `description`
   - 如果 `description` 还很空泛，就先缩小 skill 范围，不要继续扩写正文

3. 决定最小结构
   - 默认从只有 `SKILL.md` 的结构开始
   - 只有当某类信息会被反复读取或执行时，才增加 support files

4. 编写主文件
   - 主文件只保留用途、默认工作流、关键判断和重要 gotchas
   - 不把大段通识背景、长案例或可选细节堆进主文件

5. 按需补 support files
   - 只有在确实能减少重复、提升稳定性或减少主文件噪音时才添加
   - 不要为了“以后可能有用”提前创建目录和占位文件

6. 执行最小验证闭环
   - 先检查结构和触发
   - 再检查默认路径是否清楚
   - 最后用代表性请求做 dry-run 或前向测试

7. 收紧并交付
   - 如果验证暴露误触发、空话、默认路径不清或 support files 冗余，就先收紧再结束

## Support Files 决策规则

默认假设：**不需要 support files。**
只有在存在明确收益时才添加。

### `references/`

只在以下情况添加：
- 已有外部材料需要被反复引用
- 你需要把长内容从 `SKILL.md` 中移出，保持主文件聚焦
- 某份参考资料会在多个真实任务中重复使用

否则不要创建 `references/`。

### `scripts/`

只在以下情况添加：
- 某个步骤是确定性、重复性高的操作
- 现场临时重写代码明显不如预置脚本稳定
- 脚本接口可以做成非交互、可重复执行

如果当前只是定义工作流或触发描述，而不是交付可执行自动化，不要为了“完整”去加脚本。

### `assets/`

只在以下情况添加：
- 最终输出确实需要模板、脚手架或静态资源
- 这些资源会直接参与交付，而不是只是说明文档

如果资源只是帮助解释概念，不要放进 `assets/`。

## 最小验证闭环

交付前至少跑完这一轮：

1. 结构检查
   - `name` 合法且与目录一致
   - `description` 具体，不是空泛短语
   - `SKILL.md` 是否只保留当前任务真正需要的内容

2. 触发检查
   - 用 3 条不同说法快速核对 `description` 是否能命中
   - 至少覆盖：直接请求、间接请求、较口语化请求
   - 若命中范围过宽或过窄，先重写 `description`

3. 默认路径检查
   - 假设另一个 agent 只读到 `SKILL.md`
   - 它是否知道第一步做什么、默认方案是什么、什么情况下不要扩写
   - 如果前 3 步还不明确，说明正文仍然太虚

4. 噪音检查
   - 删除教程式铺垫、通用概念解释、重复表达
   - 如果一段内容不改变执行决策，就优先删或压缩

5. 代表性 dry-run
   - 选 1 个最能代表该 skill 的真实或拟真请求
   - 用当前 skill 走一遍，观察是否会误触发、跳步、扩写过度或要求过多信息
   - 若失败，优先收紧 `description`、默认路径和 gotchas，再重新检查

只有通过这轮最小验证，才把当前版本视为“可用初稿”。

## 前向测试

当环境允许、且任务成本可控时，可以使用子 agent 做前向测试。
原则如下：
- 把它当成真实任务，不要告诉子 agent 你在“测试 skill”
- 传原始请求和必要材料，不传你的结论或预期答案
- 优先观察它是否按预期理解 `description`、是否读取了正确文件、是否遵守默认路径
- 如果前向测试只有在泄漏答案后才成功，说明 skill 还不够稳

低证据路径下，前向测试的重点不是证明“它已经很强”，而是发现：
- 触发是否模糊
- 默认路径是否不够清楚
- support files 是否其实没必要
- gotchas 是否应该再前置

## 迭代与升级

低证据路径不是终态。
在后续真实使用中，重点收集这些信号：
- 用户反复使用的真实说法
- 经常补充的背景信息
- 失败案例、误触发、遗漏步骤
- 已经稳定复用的模板、脚本或参考资料

当这些材料开始稳定出现时：
- 把成功做法沉淀为默认路径
- 把反复失败点升级为更明确的 gotchas
- 把反复引用的内容拆到 support files
- 视情况把当前 skill 升级到 `references/evidence-rich.md` 的写法
