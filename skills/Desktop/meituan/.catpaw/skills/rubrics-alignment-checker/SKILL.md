# Rubrics Alignment Checker

## 适用场景
- 用户要求检查 `instruction.md`、`SKILL.md`、`rubrics.md` 是否对齐
- 用户要求审核已有 `solution/rubrics.md` 是否缺项、过度约束或存在冲突
- 任务目录符合 `instruction.md + environment/skills/*/SKILL.md + solution/rubrics.md` 的结构
- 某些题目没有 skill；此时只以 `instruction.md` 为准

## 核心原则
1. `instruction.md` 与 `SKILL.md` 是 rubric 的上游事实来源。
2. rubric 只检查最终产物中可观察到的结果，不检查模型的隐式思考过程。
3. rubric 必须完整覆盖所有显式交付要求，但不得新增来源中不存在的硬约束。
4. 数量、范围、比较符、精度、路径、文件格式、枚举值、顺序等，一旦被显式写出，必须原样保留。
5. 如果 `instruction.md` 和 `SKILL.md` 存在冲突，不要擅自裁决，先标记为冲突项。

## 来源使用顺序
- 第一优先级：`instruction.md`
- 第二优先级：`environment/skills/` 下所有 `SKILL.md`
- 第三优先级：现有 `solution/rubrics.md`，作为被审查对象
- `input/` 和参考答案只在判断“rubric 是否把已有显式要求具体化为稳定可验证结果”时作为辅助旁证
- 绝不能让参考答案反向引入 `instruction.md` 与 `SKILL.md` 没有要求的新评测维度

## 执行流程

### 第 0 步：定位题目文件
1. 读取 `instruction.md`
2. 读取 `environment/skills/*/SKILL.md`
3. 读取 `solution/rubrics.md`
4. 只有在判断 rubric 中的精确值是否属于“合法具体化”时，才读取 `input/` 或参考答案

### 第 1 步：抽取显式交付要求
只抽取会改变最终交付物的要求：
- 输出路径、文件名、扩展名
- 输出文件数量
- 必须出现的页面、章节、sheet、表头、字段、图表、模块
- 必须出现的类别、项目、枚举值
- 精确数量、最少数量、最多数量、范围、阈值
- 格式要求，如日期格式、保留小数位、百分比形式
- 可机械推导的结果值，如汇总数值、筛选后的目标项、逐行校验状态
- 只有在来源明确限定文案时，才检查精确措辞

不要把下面内容直接写成 rubric：
- 使用什么工具、库、语言实现
- 环境安装步骤
- “不要问我问题”“直接生成即可”这类交互要求
- 仅影响过程、不影响最终产物可观察结果的说明
- “推荐”“允许”“可自行发挥”这类非强制表述

### 第 2 步：归一化要求
为每条要求建立统一描述：
- `source`：来自 `instruction`、`skill` 或 `both`
- `artifact`：约束的是哪个输出文件或交付物
- `type`：`path` / `structure` / `content` / `value` / `format` / `constraint`
- `exactness`：`presence` / `exact` / `at-least` / `at-most` / `range` / `enum`
- `statement`：归一化后的自然语言要求

如果同一要求同时出现在 `instruction.md` 和 `SKILL.md` 中，只保留一条归一化要求，但要记录来源为 `both`。

### 第 3 步：判断是否允许写精确值
只有同时满足下面两点，rubric 才能写精确期望值：
1. 该评测维度本身已经被 `instruction.md` 或 `SKILL.md` 明确要求
2. 该值可以根据输入数据、规则或参考答案稳定推导出来

允许写精确值的常见情形：
- 已要求按月展示收入/支出，则 rubric 可以写 1-12 月的具体数值
- 已要求筛出差异率绝对值达到阈值的科目，则 rubric 可以写出被筛中的具体科目
- 已要求逐行校验配置状态，则 rubric 可以写每条记录对应的通过/异常结果

不允许写精确值的常见情形：
- 来源只要求“写总结”，rubric 不能擅自要求“5 条建议”
- 参考答案用了某个更漂亮的标题，但来源没有要求该标题
- 来源只说“包含苹果”，rubric 不能升级为“包含 3 个苹果”

### 第 4 步：保留语义精度
严格保留来源中的精度与比较符：
- “有苹果” -> 检查“包含苹果”，不检查数量
- “3 个苹果” -> 检查“恰好 3 个苹果”
- “至少 3 个苹果” -> 检查“>= 3”
- “不超过 3 个苹果” -> 检查“<= 3”
- “保留 2 位小数” -> 检查精确到 2 位小数
- “按指定顺序展示” -> 检查顺序
- “可自行发挥调整页数” -> 不要生成固定页数 rubric

### 第 5 步：审查 rubric
逐条比对 `solution/rubrics.md`，检查它是否满足以下规则：
- 每条 rubric 只验证可观察结果，不验证过程
- 每条 rubric 是否明确目标输出文件或交付物
- 描述是否可判定为通过或不通过
- 是否错误引入主观词或来源中不存在的限制
- 是否把来源中的可选项、推荐项误写成强制项
- 是否遗漏了来源中已经明确写出的路径、数量、格式、阈值、顺序、枚举值

如发现问题，按“缺失要求 / 过度约束 / 冲突或歧义”分类整理。

## 审核清单
在提交 rubric 的检查结果前，逐项确认：
- `instruction.md` 的显式交付要求已全部覆盖
- `SKILL.md` 的显式交付要求已全部覆盖
- 没有把可选项升级为强制项
- 没有把过程要求写成结果要求
- 没有新增来源中不存在的评测维度
- 所有数量、阈值、顺序、精度都被正确保留
- 多个 skill 同时存在时，已合并所有显式要求

## 冲突处理
如果 `instruction.md` 与 `SKILL.md` 冲突：
- 明确列出冲突项
- 不要悄悄选择其中一边
- 检查时只报告冲突，不生成修订稿，等待用户后续决定

常见冲突包括：
- 输出路径或扩展名不一致
- 页数、章节数、条目数不一致
- 一个文件说必填，另一个文件说可选
- 字段名、图表类型、输出格式不一致

## 检查输出格式
当用户要你检查已有 `rubrics.md`，直接在对话框输出检查结果，按以下顺序组织：
1. 已覆盖要求
2. 缺失要求
3. 过度约束
4. 冲突或歧义
5. 总体结论（是否对齐）

不要新建文件，不要改写项目内已有 `rubrics.md`，除非用户明确要求你修改。

## 快速示例

### 示例 1：存在即可 vs 精确数量
来源：`交付结果里要有苹果`
- 正确 rubric：`交付结果包含苹果`
- 错误 rubric：`交付结果包含 3 个苹果`

来源：`交付结果里要有 3 个苹果`
- 正确 rubric：`交付结果包含 3 个苹果`

### 示例 2：允许精确化的情况
来源要求：按季度输出收入占比饼图。
如果输入数据能唯一确定每个季度的收入占比，那么 rubric 可以写出每个季度的精确百分比。

### 示例 3：禁止过度约束
来源要求：`生成总结`
- 错误 rubric：`总结包含 5 条建议`
- 正确 rubric：`输出包含总结部分`

## `/meituan` 项目约定
在当前项目中，默认按以下方式工作：
- `/meituan` 下每个顶层目录视为一道完整测试题
- 主来源为该题目录下的 `instruction.md` 和 `environment/skills/*/SKILL.md`
- 审核目标是该题目录下已有的 `solution/rubrics.md`
- 如果题目没有 skill 文件，不要虚构 skill 约束
- 如果存在多个 skill 文件，需要合并所有显式交付要求

## 最终准则
rubric 是显式要求的可执行镜像。
检查时要判断它是否完整、不过度、无冲突：可以把已明确要求的维度具体化，但绝不能无中生有地强化要求，也不能弱化原始要求。
