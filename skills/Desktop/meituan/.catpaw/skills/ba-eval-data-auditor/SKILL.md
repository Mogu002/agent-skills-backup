# BA Eval Data Auditor

用于批量检查 BA 评测数据的 `instruction.md` 和 `solution/rubrics.md` 是否符合评测数据要求，并补充 BA 场景的固定模板检查。当前规则已吸收新增的 rubrics 专项文档，覆盖文件读取路径、`<file>` 引用、xlsx/csv 比对表述、rubric 拆分粒度，以及 instruction 与 rubrics 的逻辑自洽性、rubrics 是否过严或过于模糊等要求；同时支持根据 `message.json`/`openai_messages.json`、`score.md` 与 `solution/rubrics.md` 复核 score 判分是否正确。

## 何时使用

- 用户要求检查 `BA` 目录下所有题目或某几个 `ba-xxx` 题目
- 用户要求审计 `instruction.md` / `rubrics.md` 是否符合评测数据规范
- 用户明确怀疑 instruction 和 rubrics 没对齐，或担心 rubrics 写得过死、过虚、过于难判
- 用户希望根据 `message.json`/`openai_messages.json`、`score.md` 和 `rubrics.md` 检查某次判分是否判对了
- 用户要先看到逐题问题清单，再决定是否修改文件
- 用户希望对 BA 数据做交付前自检

## 默认工作流

1. 先判断当前任务属于哪一类：`instruction/rubrics` 规范审计，还是 `score.md` 判分复核
2. 若是规范审计，先运行脚本：`python3 scripts/validate_ba_eval_data.py --root <BA目录绝对路径>`
3. 若是判分复核，读取 `references/score-judgement-audit.md`，按其中流程比对 `message.json`/`openai_messages.json`、`score.md` 与 `solution/rubrics.md`
4. 对规范审计任务，先看 `ERROR`，这些通常代表明确不符合规范或会影响机评
5. 再看描述型 rubric 是否存在明显病句、句式不通或不可判定的表达；这类问题应优先当成错误处理
6. 再看 instruction 与 rubrics 是否逻辑自洽：题目要求的分析对象、比较维度、结论维度，是否都被 rubrics 直接约束
7. 再看 rubrics 是否过严或过虚：分析/比较题若被全写成 `唯一答案：`，或描述型 rubric 只写“答案需合理/完整/准确”等空泛要求，都应重点复核
8. 再看 `WARNING`，这些通常代表表述不严谨、模板不一致或需要人工复核
9. 若脚本提示 `BA_FILL_BLANK_COUNT`，默认按“拆分粒度提醒”处理，不计入错误；只有结合题意确认 rubrics 确实漏拆或错拆时，才作为需要修改的问题
10. 若用户只想检查单题，追加 `--only ba-054`
11. 若用户需要结构化结果，追加 `--format json`
12. 对分析题，结合 `instruction` 的任务要求，人工确认 rubrics 是否按逻辑层次拆分；若脚本提示分析题少拆或层次遗漏，优先按“识别对象/事实 → 分析效果或原因 → 结论/建议”去复核
13. 若 `instruction` 明确要求开放分析或归因推断，例如“推断最可能发生了什么事件”“说明各指标之间的因果链路”，不要把整题 rubrics 全部写成 `唯一答案：`；至少应有一条 `答案需...` / `答案内容需...` 类型 rubric 去校验开放分析维度
14. 若脚本提示 `BA_DWD_QUERY_RISK`，优先判断题目是否把“品类/入口/商品”这类只能从 `dwd_transaction` 拿到的明细维度，和“驱动/归因/比较/最高最低”这类全量判定绑定在一起；这类题即使格式合规，也可能因为 `SQL Interrupted` 导致 rubric 不可靠

## 脚本会检查什么

### 目录结构

- 每个 `ba-xxx` 目录是否存在 `instruction.md`
- 每个 `ba-xxx` 目录是否存在 `solution/rubrics.md`

### instruction 规范

- 文件非空
- 含防追问要求：`不要问我任何问题`、`不要让我做出进一步决策`、`请你自行解决`
- 若出现本地文件路径，路径是否为 `/meituan/...` 形式
- 若看起来是本地文件输出/修改任务，是否明确文件路径或文件夹路径
- BA 固定结构是否齐全：角色说明、Datasette SQL 接口、三张表说明、在线浏览地址、`任务要求：`、收尾注意事项

### rubrics 规范

- 标题是否为 `# Rubrics`
- 是否包含通过标准说明
- 是否包含 `## 文件读取路径`
- 是否存在且仅存在一个 `json` 代码块
- `json` 代码块是否为单个数组，且数组元素均为对象
- 每条 rubric 是否包含 `id`、`content`、`weight`
- `id` 是否唯一且符合两位数字格式
- `weight` 是否为正数
- `<file>...</file>` 引用是否与 `## 文件读取路径` 中列出的路径一致
- 文件读取路径是否逐行列出、避免多余目录、通配符是否只在必要时用 `/*`
- rubric 是否错误要求模型自行检查路径、读取文件或遍历目录
- 是否引用 zip 文件进行比对
- rubric 数量是否原则上不超过 5 条
- rubric 是否把过多判断塞进同一条，是否需要拆分
- instruction 中填空槽数量与 rubrics 条数是否明显不一致；这项仅用于提示拆分粒度风险，默认记为 warning，不计入 error
- 对分析题，rubric 是否按独立逻辑层次拆分；默认优先检查是否至少覆盖“识别对象/事实”“分析效果或原因”“给出结论/建议”中的相关层次，而不是把多层逻辑压成 1 条
- 对开放分析/归因题，若 `instruction` 要求“推断事件”“说明因果链路”“综合以上分析”等开放作答，rubrics 不应全部使用 `唯一答案：`；至少要有 1 条 `答案需...` / `答案内容需...` 类型 rubric 直接校验事件判断、因果链路或分析过程
- rubric 内容是否含明显模糊词
- instruction 与 rubrics 是否逻辑自洽：instruction 要求的分析对象、比较对象、答题维度，rubrics 是否都有直接对应
- instruction 若明确要求按城市/对象分别比较，rubric 是否真的约束了“比较/分别/分城市”而不是只给单点结论
- instruction 若明确要求回答“运营策略”或“效果正/负面”等分析维度，rubric 是否直接覆盖这些维度，避免把结论写死却漏掉题目要求本身
- 是否存在 `dwd_transaction` 查询风险：题目是否要求对“品类/入口/商品”等 DWD 明细维度做驱动归因、全量比较、排序或最高/最低判断，而 rubrics 又写成唯一答案；这类题在当前 Datasette 上容易触发 `SQL Interrupted`
- 分析/比较题是否被写得过严：rubrics 是否不当地全部使用 `唯一答案：`，把开放分析压成单一结论
- 描述型 rubric 是否过于模糊：是否只写“答案需合理/完整/准确”等抽象要求，而没有可观察、可判定的核心要素
- xlsx/csv 比对表述是否合理：csv 不应承担格式判断，xlsx 的格式判断应明确到列/行/单元格范围
- 涉及日期/百分比/分数/会计等格式时，是否明确写成“单元格格式”并给出具体要求
- 是否出现单元格透明度判断
- solution 文件名若与 input 重名，是否缺少“参考答案”后缀提示
- BA 场景下，rubric 内容是否采用明确校验前缀开头，例如 `唯一答案：`、`答案需`、`答案内容需`
- 对描述型 rubric，`答案需...` 或 `答案内容需...` 后是否是通顺、可判定的要求句，是否像“答案需明确指出……”“答案需提及……”“答案需说明……”这样直接描述答案应包含的核心要素；像“答案需需求上升导致供给偏紧”这类句式不通的表述应视为错误

## 重要 gotchas

- 优先相信脚本的全量扫描结果，不要只抽样看 1-2 个题目
- `WARNING` 不一定要立刻修改，但交付前最好逐条解释清楚
- 当前脚本只做检查，不会自动改文件
- 对分析题/归因题，除了看 rubric 结论对不对，还要看 rubric 是否真的对齐了题目要求的分析对象；例如题目问“采取了什么运营策略”，rubric 也应直接校验“策略”维度，而不只是写一个可能的具体动作
- 若 instruction 明确要求“比较/分别分析/分城市观察”，而 rubrics 只写单个结论、不约束比较对象或比较维度，应视为 instruction 与 rubrics 不自洽
- 若分析题/比较题全部写成 `唯一答案：`，优先判断是否把本应开放的分析过程写死；这通常不是格式错，而是 rubric 过严
- 若脚本报 `BA_DWD_QUERY_RISK`，默认先按“高风险 warning”处理：它不代表题目一定错误，但代表作答者可能无法仅凭题内 `sql_url` 稳定复现 rubric 证据，交付前应人工复核是否需要回退到 DWS 题型、补显式汇总结果或放宽 rubric
- `BA_FILL_BLANK_COUNT` 只表示填空槽数量与 rubric 条数看起来不一致，默认不计入错误；分析题、复合题或“若干填空 + 1 条总结性 rubric”的设计都可能是合理的，需结合题意人工判断
- 若题目要求“推断最可能发生了什么事件”“说明因果链路”这类开放分析，不要因为前面有若干数值填空，就把整题 rubrics 都写成 `唯一答案：`；开放分析部分应至少单独有一条 `答案需...` / `答案内容需...` rubric
- `ba-seed-generator` 的默认做法是把分析题拆成逻辑层次；审计时不要只看字面答案是否正确，还要看 rubrics 是否少拆、漏掉关键层次，尤其是“识别对象/事实 → 分析效果或原因 → 结论/建议”这类链路
- 描述型 rubric 不仅要以 `答案需...` 开头，还要写成自然、可判定的要求句，优先使用“答案需明确指出……”“答案需提及……”“答案需说明……”等句式，避免把结论或原因裸接在 `答案需` 后面
- 仅写“答案需合理/完整/准确/清晰”等抽象词，通常不足以支持稳定机评；除非后面紧跟具体观察点，否则优先当成“过于模糊”处理
- 只有在 rubrics 需要读取模型输出文件或参考答案文件时，`## 文件读取路径` 才应该非空
- 若 xlsx rubric 既写“完全一致”又没说明是内容/数值还是格式，优先当成表述风险处理
- 若某题是刻意偏离 BA 固定模板的例外题，请先确认是否为真实例外，再决定修改题目还是调整脚本

## 建议输出方式

向用户汇报时，优先给：

- 总扫描题目数
- 有问题的题目数
- `ERROR` / `WARNING` 数量
- 每个题目的问题列表
- 若没有发现问题，也要明确说明仅代表格式、可机评性与显式自洽性通过，不代表业务逻辑一定正确
