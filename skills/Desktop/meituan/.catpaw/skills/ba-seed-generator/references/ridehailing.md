# BA 种子数据生成 Guide（ridehailing）

## 功能说明

本 Skill 接收来自**两个关联表格**的输入，生成两个文件：

1. **`instruction.md`**：任务指令文件，包含数据库接口地址、三张表的完整字段说明（内嵌）、任务要求。
2. **`solution/rubrics.md`**：评分标准文件，JSON 内容按评分点拆分为多个对象。

> **格式基准**：以 `instruction(1).md` 为模板，所有固定文字原样输出，仅替换变量部分。

并遵循以下默认出题导向：

- 对**综合分析 / 下钻归因 / 运营策略 / 外部事件 / 相关性 / 高难生成**类题目，默认优先生成**业务判断型题干**：直接问最终业务问题或目标是否达成，不提前把中间计算路径拆成教程式步骤。
- 对**计算题 / 填空题 / 异动识别**类题目，可以保留明确的计算或定位指令。
- 只有当用户明确要求“生成表格 / 画图 / 分步骤回答 / 逐项计算 / 固定输出字段”时，才在题干中写入结构化的中间步骤要求。

---

## 剧本设计与题目构建流程

当用户不是直接给出 `question` / `reference_answer`，而是只给剧本目录、数据表、难度和题型要求时，先完成这一段上游设计，再回到后续文件生成步骤。

### 0.1 先读剧本，识别主线矛盾

先基于三张表识别这个剧本到底在讲什么，再决定题目问什么。

优先回答以下问题：

- 异动从**哪一天 / 哪个阶段**开始，是否存在明显冲击窗口或策略切换窗口。
- 主要矛盾更偏**供给侧 / 需求侧 / 定价补贴 / 漏斗效率 / 城市差异 / 时段结构**中的哪一类。
- 影响最大的对象是谁：城市、时段、订单场景、司机 / 乘客生命周期人群、平台整体指标，还是它们的组合。
- 数据里是否存在可以稳定复现的**唯一业务结论**，以及该结论依赖哪些关键证据。

### 0.2 先定答案，再定题目

默认先写出 `reference_answer` 的核心结论，再反推 `question`，不要先拍脑袋写题面。

建议顺序：

1. 先用数据找出最稳的最终结论。
2. 再补上支撑这个结论的 2-3 个关键证据。
3. 最后把它改写成用户真实会问的业务问题。

如果一个问题在不提示中间计算步骤的情况下仍然能得到**客观唯一**的最终结论，就优先采用这种问法。

### 0.3 按难度选择题目承载方式

- **简单题 = L1（精确计算）**：优先承载单事实、单时间点、单指标异动、单对象识别。答案应为唯一数值或唯一枚举，可直接从数据计算得出。
- **中等题 = L2（结构化分析）**：优先承载漏斗拆解、维度拆解、贡献分析、事件识别等框架型问题。答案可以有限开放，但必要分析维度应可穷举。
- **困难题 = L3（综合判断）**：优先承载经营解读、策略取舍、优先级判断、方案设计等需要业务决策的问题。过程可以开放，但 rubrics 必须锚定关键洞察或结论。
- 如果题目的核心是精确计算，即使补一句解释，也不要升级到 L2。
- 如果题目的核心是框架拆解而非经营决策，不要升级到 L3。
- 如果用户要求更高难度，但现有证据不足以支撑稳定判断，优先降级到能唯一判定的层级，不要为了凑难度硬写题目。

### 0.4 题干设计原则

- 优先写**最终业务问题**，而不是把计算过程写成说明书。
- 优先问“是否达成目标 / 问题更像供给侧还是需求侧 / 最该保留什么 / 最该收缩什么 / 最需要优先处理哪个城市、场景或时段”。
- 只有在题目的本质就是考计算、填空、表格输出、图表输出、固定字段生成时，才显式暴露中间步骤。
- 如果题目要求是分析 / 归因 / 判断，不要默认写成“先算 A、再算 B、再比较 C”。
- 题干保持模糊到接近真实业务，但不能模糊到出现多个同样合理的标准答案。

### 0.5 rubrics 反向校准

在 `question` 写完后，立即检查：

- rubrics 是否锚定了**最终结论**，而不只是锚定中间计算量。
- rubrics 是否覆盖了支撑结论所需的关键证据。
- 若题目是分析题，rubrics 是否覆盖“结论 -> 证据 -> 原因 / 影响 / 建议”中的必要层次。
- 若题目是高难生成题，是否通过固定格式与 tie-break 规则消除了并列答案。

### 0.6 最小自检

出题完成后至少做这 4 个检查：

1. 不看 `reference_answer`，只看 `question`，像不像真实业务同学会提的问题。
2. 不看中间计算过程，结论是否仍然唯一。
3. `question` 与难度是否匹配：中高难题不能靠手把手提示完成。
4. rubrics 是否在不过度教程化的前提下，仍能稳定机评。

## Step 1：读取表格输入

如果用户给的是“剧本目录 + 难度/题型要求”，而不是现成的 `question` / `reference_answer`，先执行上一节的剧本设计与题目构建流程，产出题面与参考答案后，再继续本步骤。

1. 读取**表格 A**，获取 `题号`、`合成数据编号Case Id`、`原可用数据对应Data Id`、`data_url`。
2. 读取**表格 B**，获取 `question`、`reference_answer`、`Case Id`、`Data Id`。
3. 通过 **`合成数据编号Case Id` = `Case Id` 且 `原可用数据对应Data Id` = `Data Id`** 关联两张表。
4. 对每个关联结果推导变量，其中 `browser_url` 取 `data_url` 的域名部分加 `/`。

## Step 1.5：确定题干风格

在生成 `question` 前，先判断题目应该采用哪种问法。

1. 先结合用户指定的**题型**与**难度**，判断该题更适合“直答型题干”还是“业务判断型题干”。
2. 若题目属于**综合分析 / 下钻归因 / 运营策略 / 外部事件 / 相关性 / 困难生成**，默认使用**结论导向、过程开放**的问法。
3. 题干应尽量贴近真实业务表达，例如：`是否达成了某目标`、`问题更像供给侧还是需求侧`、`最需要优先处置的城市、场景或时段是哪一个`、`应继续还是停止某策略`。
4. 不要把“先算 A、再算 B、再比较 C、最后给建议”整串写进题干；如果删掉这些中间步骤后，题目仍能被唯一回答，就应删掉。
5. 客观唯一性优先通过 `reference_answer` 与 rubrics 锚定**最终结论**和**关键证据**来保证，而不是通过在 `question` 中显式教 agent 怎么算。
6. 只有在用户明确要求**填空 / 计算 / 表格 / 图表 / 固定字段输出 / 分步骤回答**时，才改用结构化、显式拆解的题干。

## Step 4：rubrics content 的拆分规则

### 4.1 判断题型

先读取 `question` 字段，判断题型：

| 题型 | 判断依据 |
|---|---|
| **填空题** | `question` 中含 `______` 填空槽 |
| **计算题** | `question` 要求给出具体数值、百分比、时间点或定位结果，且通常显式要求计算或识别 |
| **分析题** | `question` 要求对目标是否达成、问题归因、事件判断、策略优先级、影响或建议做业务结论；题面可以不显式给出中间计算步骤 |
| **简单问答** | `question` 要求识别单一事实或概念 |

### 4.2 拆分粒度

- **填空题**：每个 `______` 槽对应一个 rubric 对象。
- **计算题**：每个题面明确要求的独立数值结论对应一个 rubric 对象；不要为题面未要求的隐含中间量强行拆分。
- **分析题**：按“业务结论 -> 关键证据 -> 原因 / 影响 / 建议”拆分为多个 rubric 对象；不要机械复写题面中不存在的中间计算步骤。
- **简单问答**：通常 1 个 rubric 对象。

**各 id 之间考察内容不得重叠。**

### 4.3 content 写法规范

#### 范式 A：直答型（填空题、计算题）

以 `唯一答案：` 开头，后接正确答案。若有多种等价写法，用 `或` 连接。

示例：

```json
{ "id": "01", "content": "唯一答案：第11天", "weight": 1 }
{ "id": "02", "content": "唯一答案：第20天", "weight": 1 }
```

#### 范式 B：描述型（分析题、开放题）

以 `答案需` 开头，描述答案必须覆盖的核心要素。

示例：

```json
{ "id": "01", "content": "答案需明确指出出现策略异动的城市为北京和上海", "weight": 1 }
{ "id": "02", "content": "答案需说明北京侧策略带来了新客曝光和成单增长且平台净收入保持健康，上海侧策略导致司机补贴抬升、平台净收入承压", "weight": 1 }
```

### 4.4 修改前备份（仅对已存在的 `rubrics.md` 执行）

在修改任何已存在的 `rubrics.md` 之前，将原始 JSON 数组以 HTML 注释形式追加到文件末尾：

```
<!-- ORIGINAL RUBRICS (修改前备份，请勿删除)
[
  {
    "id": "01",
    "content": "原始内容...",
    "weight": 1
  }
]
-->
```

## 执行注意事项

1. **三张表的字段说明内容固定**，只替换表名中的 `case_id` 数字，其余字段描述文字一字不改。
2. **`browser_url` 由 `data_url` 自动推导**，取域名部分加 `/`，无需单独输入。
3. **直答型 content 必须以 `唯一答案：` 开头**，不得裸写答案。
