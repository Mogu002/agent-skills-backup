# BA 种子数据生成 SOP（specialteam）

## 1. 目标与产出

本 SOP 用于指导 agent 在特团场景下生成两个文件：

1. **`instruction.md`**：任务指令文件，包含本地数据使用说明、四张表的完整字段说明（内嵌）、任务要求。
2. **`solution/rubrics.md`**：评分标准文件，JSON 内容按评分点拆分为多个对象。

### 1.1 默认执行原则

- 当用户未直接提供现成 `question` / `reference_answer`，而是要求基于特团剧本、方向、难度、题型来构题时，若工作区存在 `题目指纹与防重地图.md`，先读取它，识别已覆盖场景、对象、问法与高相似题型，再决定候选题方向。
- 默认优先使用工作区中的预置剧本总结文件（当前约定为 `特团MVP沙盒及剧本更新.md`）作为**剧本事实源**，用于理解：有哪些剧本、哪些字段会变化、这些字段如何相互影响；不要把它当成可直接抄数值答案的数据源。
- 预置剧本总结文件只负责提供剧本机制、比较窗口、字段变化方式与业务逻辑，不负责提供最终题目答案；题目中的数据、结论、时间点、排序结果和 rubrics 中的精确数字，必须回到底层本地数据表核对后再落盘。
- 先从文件里的 `剧本设计`、`生效期`、`自变量调整`、`效果` 提炼主线矛盾、比较窗口、字段变化和稳定结果，再据此决定应该去哪些本地底表验证。
- 只要这些信息足以帮助你锁定候选方向，就直接进入“候选答案 -> 本地底表核对 -> 候选题面”的流程；不要切换到在线数据库 / Datasette / SQL 路径。
- `题目指纹与防重地图.md` 只用于已有题覆盖扫描，不替代本 SOP 的构题规范与格式要求。

### 1.2 输出格式要求

> **格式基准**：沿用当前 BA 种子数据模板结构；所有固定文字原样输出，仅替换变量部分。

### 1.3 默认出题导向

- 对**综合分析 / 下钻归因 / 运营策略 / 外部事件 / 相关性 / 高难生成**类题目，默认优先生成**业务判断型题干**：直接问最终业务问题或目标是否达成，不提前把中间计算路径拆成教程式步骤。
- 这类业务判断型题干默认先在内部补齐“**比较窗口 + 对象粒度 + 必要的 tie-break / 排序规则**”这一层，再优先把这些约束压缩成自然的业务限定语写进题干；避免使用“口径规定：”“统一比较”“按以下步骤判断”等显式教程式措辞。除非不补具体指标就会出现多个同样合理的答案，否则不要在题干中直接指定必须比较的字段或完整 if-then 判定逻辑；禁止直接使用未定义的“有效拉新”“效率不恶化”“值得保留”“应收缩”等抽象表述。
- 对**计算题 / 填空题 / 异动识别**类题目，可以保留明确的计算或定位指令。
- 只有当用户明确要求“生成表格 / 画图 / 分步骤回答 / 逐项计算 / 固定输出字段”时，才在题干中写入结构化的中间步骤要求。

## 2. 标准流程一：先完成剧本理解与构题

当用户不是直接给出 `question` / `reference_answer`，而是只给剧本方向、难度和题型要求时，先完成这一段上游设计，再回到后续文件生成步骤。

这里提到的 `question` / `reference_answer` 有两种来源：
- 用户直接提供的现成题面与标准答案
- agent 基于预置剧本总结文件 + 本地底表先内部拟出的**候选题面**与**候选标准答案**

本节讨论的是第二种情况，也就是从“预置剧本资料 -> 本地底表核对 -> 候选答案 -> 候选题面 -> 最终 instruction / rubrics”的内部构题过程，而不是要求用户额外输入题干或参考答案。

### 2.0 先过防重地图

当任务是“先构题再落盘”，且工作区存在 `题目指纹与防重地图.md` 时，先做一次已有题覆盖扫描，再进入剧本理解。

最少完成三件事：
1. 找出与当前剧本方向最接近的已有题，明确它们分别占用了哪些场景、对象、层级和问法。
2. 标出本次不应继续走的方向，尤其是已在场景、矛盾、对象、层级、问法中重合 3 项及以上的高相似坑位。
3. 明确本次更适合从哪个未充分覆盖的方向切入，例如档口结构迁移、城市异质性、生命周期迁移、二阶影响、实验可信度。

只有完成这一步，才能进入候选 `reference_answer` / `question` 的正式设计。

### 2.1 先读剧本，识别主线矛盾

默认先读 `特团MVP沙盒及剧本更新.md` 中对应剧本段落，再决定题目问什么。预置剧本总结文件的职责是帮助你识别剧本机制，不是让你直接引用其中出现的数字当作答案。

如果前一步已完成防重扫描，这里要继续确保：你从剧本中提炼出来的候选方向，确实没有重新落回刚刚排除掉的高相似坑位。

按用户给定剧本名称，默认优先定位以下段落：
- `供给侧冲击` -> 剧本1（case 02）
- `新客冷启动加速` -> 剧本2（case 03）
- `用户留存恶化` -> 剧本3（case 04）
- `货盘折扣收缩` -> 剧本4（case 01）
- `体育赛事需求冲击` -> 剧本5（case 05）

优先先从预置剧本文件抽取以下四类信息：
- `剧本设计`：主线矛盾、业务机制、最核心的受影响对象
- `生效期`：冲击窗口、恢复窗口、适合做比较的时间切片
- `自变量调整`：被改动的字段、对象粒度和可下钻方向
- `效果`：可能出现的结果方向、影响链路和候选证据

在此基础上，再回答以下问题：
- 异动从**哪一天 / 哪个阶段**开始，是否存在明显冲击窗口或策略切换窗口
- 主要矛盾更偏**供给侧 / 需求侧 / 补贴结构 / 漏斗效率 / 城市差异 / 入口策略**中的哪一类
- 影响最大的对象是谁：城市、入口、生命周期人群、档口状态、平台整体指标，还是它们的组合
- 若要得到唯一业务结论，还需要回到哪些本地底表核对哪些字段

### 2.2 先定候选标准答案，再定候选题面

默认先写出候选 `reference_answer` 的核心结论，再反推候选 `question`，不要先拍脑袋写题面。

前提是：你已经先过一遍 `题目指纹与防重地图.md`，确认当前候选方向没有与已有题形成高相似重叠；若已重叠，先换方向，再继续写候选答案。

建议顺序：
1. 先基于剧本机制写出**候选最终结论**
2. 再到本地底表核对支撑这个结论的 2-3 个关键证据
3. 若题目需要精确数字、百分比、时间点、排序结果，再继续用本地底表把这些答案核实到可机评
4. 最后把它改写成用户真实会问的业务问题

如果一个问题在不提示中间计算步骤的情况下仍然能得到**客观唯一**的最终结论，就优先采用这种问法。

### 2.2.1 先做口径消歧

只要你**正在拟定的候选题干**或**候选标准答案草稿**里出现以下任一类词，先停下来补全口径，再继续出题：`有效拉新`、`效率不恶化`、`健康`、`显著`、`更优`、`最值得保留`、`最应收缩`、`高质量增长`、`达成目标` 等。

默认先补齐以下三件事：
1. **比较窗口**：与谁比，是前后阶段、基线期、均值，还是阈值。
2. **对象粒度**：平台 / 城市 / 入口 / 城市-入口 / 人群，只选一种默认粒度，不要混写。
3. **排序规则 / tie-break**：当题目要求“最值得保留 / 最应收缩 / 最优先处理”时，写清并列时如何决策。

补完这三类口径后，优先把它们改写成自然题面，而不是另起一句“口径规定：……”。

然后做一次唯一性检查：
4. **最小化补充约束**：如果只靠前三项仍可能出现多个同样合理的标准答案，再补充必要的判断指标、阈值或观察范围；能不写进题干就不要写进题干。

如果上述约束仍无法明确，就不要继续沿用该抽象说法。

### 2.3 按难度选择题目承载方式

- **简单题**：优先承载单事实、单时间点、单指标异动、单对象识别。答案应短、唯一、稳定。
- **中等题**：优先承载业务判断、下钻归因、策略效果判断、事件识别。题面可以开放，但结论必须可唯一锚定。
- **困难题**：优先承载生成类且唯一答案的任务。通常通过固定输出格式、明确 tie-break 规则、限定观察范围，保证只有一个标准答案。

### 2.4 题干设计原则

- 优先写**最终业务问题**，而不是把计算过程写成说明书。
- 优先问“是否达成目标 / 更像什么问题 / 最该保留什么 / 最该收缩什么 / 最需要优先处理谁”，但如果这样问，默认先把比较窗口、对象粒度和必要的 tie-break 融进自然业务语句；除非不补具体指标就无法保证唯一答案，否则不要直接把必须比较的字段、完整判定逻辑或“口径规定：”式说明写成题面。
- 只有在题目的本质就是考计算、填空、表格输出、图表输出、固定字段生成时，才显式暴露中间步骤。
- 如果题目要求是分析 / 归因 / 判断，不要默认写成“先算A、再算B、再比较C”。
- 不要同时混用“城市或入口”“城市/入口/人群”这类多粒度对象；默认固定到一种比较粒度，只有用户明确要求跨粒度时才混用。
- 将“显著 / 健康 / 恶化 / 更优 / 高效”优先替换成比较窗口、排序规则、对比基线或观察范围；仅在这些仍不足以唯一时，才补阈值或具体指标。
- 题干保持模糊到接近真实业务，但不能模糊到出现多个同样合理的标准答案。

### 2.5 rubrics 反向校准

在候选 `question` 写完后，立即检查：
- rubrics 是否锚定了**最终结论**，而不只是锚定中间计算量
- `question` 里的抽象目标是否至少已经被显式翻译成比较窗口、对象粒度和必要的 tie-break；若仍不足以唯一，再最小化补充判断指标、阈值或观察范围
- rubrics 是否完整复用了同一套口径，而不是在评分时临时换了一套解释
- rubrics 是否覆盖了支撑结论所需的关键证据
- 若题目涉及精确数值，rubrics 是否明确基于本地底表核对后的答案，而不是照抄剧本总结中的描述
- 若题目是高难生成题，是否通过固定格式与 tie-break 规则消除了并列答案

### 2.6 最小自检

出题完成后至少做这 7 个检查：
1. 不看候选 `reference_answer`，只看候选 `question`，像不像真实业务同学会提的问题
2. 题干里的每个抽象词，是否都能追溯到明确的比较窗口、对象粒度和必要的 tie-break；若仍不足以唯一，才额外补充判断指标或阈值
3. 不看中间计算过程，结论是否仍然唯一
4. 候选题是否与任一已有题在“场景、矛盾、对象、层级、问法”中重合 3 项及以上；若是，必须换题
5. 若题目含精确数字、百分比、时间点、排序结果，是否已经回到底表完成核对
6. 候选 `question` 与难度是否匹配：中高难题不能靠手把手提示完成
7. rubrics 是否在不过度教程化的前提下，仍能稳定机评

## 3. 输入资料与本地取数路径

本 SOP 只支持本地资料路径，不走在线数据库 / Datasette / SQL。

### 3.1 本地路径：预置剧本总结文件

默认读取工作区中的 `特团MVP沙盒及剧本更新.md`，按用户指定剧本定位对应段落。

| 文件段落 | 默认用途 |
|---|---|
| `剧本设计` | 识别主线矛盾、业务机制、最核心的受影响对象 |
| `生效期` | 提取冲击窗口、恢复窗口、适合做比较的时间切片 |
| `自变量调整` | 提取被修改的字段、对象粒度和可下钻方向 |
| `效果` | 提取候选结果方向、影响链路和验证线索 |

只要这份文件已足以帮助你锁定问题方向，就直接进入候选 `reference_answer` -> 本地底表核对 -> 候选 `question` 的内部构题，不要把文件里的描述性数字直接当成答案。

### 3.2 本地路径：数据底表 / 汇总表

当出现以下任一场景时，继续读取工作区中的本地底表或本地汇总表：
- 需要把候选业务结论核对到可稳定复现的证据
- 需要补齐精确数值、百分比、时间点、排序结果
- 预置剧本总结文件只给了方向，但不足以直接形成唯一答案
- 用户已经直接给了 `question` / `reference_answer`，但仍需根据本地数据检查机评稳定性

优先原则：
- 先根据剧本机制确定要验证哪些字段，再去读对应本地表
- 先用最小范围的本地数据完成核对，不要为了“更全面”展开无关字段
- 凡是会写进 `reference_answer` 或 `rubrics.md` 的精确数字，都必须能从本地底表或本地汇总表复算出来

### 3.3 本地变量清单

| 变量名 | 来源 | 说明 |
|---|---|---|
| `ba_id` | 用户指定或目标文件夹 | 目标题目目录编号 |
| `question` | 用户输入或内部构题结果 | 任务要求文字 |
| `reference_answer` | 用户输入或内部构题结果 | 参考答案 |
| `local_data_source_desc` | 工作区中的本地底表 / 汇总表说明 | 用于写入 `instruction.md` 的数据来源描述 |

## 4. 标准流程二：读取输入并补齐变量

如果用户给的是“剧本方向 + 难度 / 题型要求”，而不是现成的 `question` / `reference_answer`，先执行上一节的剧本设计与题目构建流程，先内部产出候选题面与候选标准答案，再继续本步骤。

1. 若工作区存在 `特团MVP沙盒及剧本更新.md`，且用户给的是剧本方向 / 难度 / 题型要求，默认先读该文件中对应剧本段落。
2. 从预置剧本段落中先抽取 `剧本设计`、`生效期`、`自变量调整`、`效果` 四类信息，并据此形成候选方向。
3. 若候选答案涉及精确数字、百分比、时间点、排序结果，或当前证据不足以唯一化结论，再继续读取对应的本地底表 / 汇总表完成核对。
4. 若用户已直接提供 `question` / `reference_answer`，可跳过上一步的构题，但若答案里涉及精确数字，仍需回到底表核对。
5. 生成 `instruction.md` 时补齐 `ba_id`、`question`、`reference_answer` 与 `local_data_source_desc`。
6. 不要把剧本总结文件中的结果描述直接落到最终答案；只有经本地底表核对后的内容才能进入最终 `reference_answer` / `rubrics.md`。

## 5. 标准流程三：确定题干风格

在生成 `question` 前，先判断题目应该采用哪种问法。

1. 先结合用户指定的**题型**与**难度**，判断该题更适合“直答型题干”还是“业务判断型题干”。
2. 若题目属于**综合分析 / 下钻归因 / 运营策略 / 外部事件 / 相关性 / 困难生成**，默认使用**结论导向、过程开放**的问法。
3. 题干应尽量贴近真实业务表达，例如：`是否达成了某目标`、`问题更像供给侧还是需求侧`、`最需要优先处置的城市是哪一个`、`应继续还是停止某策略`。
4. 如果题干里出现“达成目标 / 最值得保留 / 最应收缩 / 显著 / 健康 / 恶化”等抽象词，默认先显式补齐比较窗口、对象粒度和必要的 tie-break，但落到题面时优先改写成自然的业务限定语；除非不补具体指标就会出现多个同样合理的答案，否则不要直接规定必须比较的字段、完整 if-then 判定逻辑，或使用“口径规定：”这类教程式提示。
5. 可优先使用“从平台整体看 / 下钻到城市 / 相较前10天 / 若只保留一个对象 / 如有并列取变化幅度更大者”这类自然表达，把口径藏在限定条件里，而不是写成操作说明。
6. 默认固定一种比较粒度；不要写“城市或入口”这类混合槽位，除非用户明确要求跨粒度比较，且你已经给出统一 tie-break。
7. 不要把“先算 A、再算 B、再比较 C、最后给建议”整串写进题干；如果删掉这些中间步骤后，题目仍能被唯一回答，就应删掉。
8. 客观唯一性优先通过 `reference_answer` 与 rubrics 锚定**最终结论**和**关键证据**来保证；rubrics 可以锚定支撑结论的证据，但不要在评分时补进题干未声明的新判定口径。
9. 只有在用户明确要求**填空 / 计算 / 表格 / 图表 / 固定字段输出 / 分步骤回答**时，才改用结构化、显式拆解的题干。

## 6. 标准流程四：生成 `instruction.md`

以下固定文字原样输出，仅替换尖括号变量。

### 第1段：角色声明

```
你是一名专业商分分析师。请仅基于给定输入数据和业务知识完成特团业务分析，不使用任何外部信息，也不要追问补充背景。
```

### 第2段：本地数据说明

```
输入数据为工作区内提供的本地底表 / 汇总表。请仅基于这些本地数据完成分析，不要自行构造外部数据来源，也不要假设可以访问在线数据库。
```

```
本地数据说明：<local_data_source_desc>
```

### 第3段：数据库表结构

```

## 8. 标准流程六：拆分 rubrics content

### 8.1 判断题型

| 题型 | 判断依据 |
|---|---|
| **填空题** | `question` 中含 `______` 填空槽 |
| **计算题** | `question` 要求给出具体数值、百分比、时间点或定位结果，且通常显式要求计算或识别 |
| **分析题** | `question` 要求对目标是否达成、问题归因、事件判断、策略优先级、影响或建议做业务结论；题面可以不显式给出中间计算步骤 |
| **简单问答** | `question` 要求识别单一事实或概念 |

### 8.2 拆分粒度

- **填空题**：每个 `______` 槽对应一个 rubric 对象。
- **计算题**：每个题面明确要求的独立数值结论对应一个 rubric 对象；不要为题面未要求的隐含中间量强行拆分。
- **分析题**：按“业务结论 -> 关键证据 -> 原因 / 影响 / 建议”拆分为多个 rubric 对象；若题干定义了目标口径、比较窗口或 tie-break，rubrics 必须逐项复用这些定义；不要机械复写题面中不存在的中间计算步骤。
- **简单问答**：通常 1 个 rubric 对象。

**各 id 之间考察内容不得重叠。**

### 8.3 content 写法规范

#### 范式 A：直答型（填空题、计算题）

以 `唯一答案：` 开头，后接正确答案。若有多种等价写法，用 `或` 连接。

#### 范式 B：描述型（分析题、开放题）

以 `答案需` 开头，描述答案必须覆盖的核心要素。

### 8.4 修改前备份（仅对已存在的 `rubrics.md` 执行）

在修改任何已存在的 `rubrics.md` 之前，将原始 JSON 数组以 HTML 注释形式追加到文件末尾：

```
<!-- ORIGINAL RUBRICS (修改前备份，请勿删除)
[
  {
    "id": "01",
    "content": "原始内容...",
    "weight": 1
  }
]
-->
```

## 10. 最终检查清单

1. **四张表的字段说明内容固定**，表名、字段定义和指标口径都直接原样输出，不做任何改写。
2. **`特团MVP沙盒及剧本更新.md` 只用于理解剧本与字段变化，不可直接照抄其中的数字作为答案。**
3. **凡是要写进 `reference_answer` 或 rubrics 的精确数字、百分比、时间点、排序结果，都必须先回到底表核对。**
4. **直答型 content 必须以 `唯一答案：` 开头**，不得裸写答案。
5. **描述型 content 必须以 `答案需` 开头**，确保可判断性。
6. 对**综合分析 / 下钻归因 / 运营策略 / 外部事件 / 相关性**类题目，默认优先生成**结论导向、过程开放**的真实业务问法，不要把中间计算步骤写得过细，除非用户明确要求。
7. 这类题目的客观唯一性，优先依靠 `reference_answer` 与 rubrics 锚定最终结论和关键证据，而不是依赖题干中的教程式计算提示。
8. **凡是题干或 rubrics 中出现“显著 / 健康 / 恶化 / 有效拉新 / 最值得保留 / 最应收缩 / 达成目标”等抽象词，默认先写清比较窗口、对象粒度和必要的 tie-break；只有这些仍不足以保证唯一答案时，才最小化补充具体判断指标、阈值或观察范围。若这些口径需要出现在题干里，优先改写成自然的业务限定语，不要使用“口径规定：”或“统一比较……”这类显式教程式表达。**
9. **默认固定一种比较粒度**；不要写“城市或入口”这类混合槽位，除非用户明确要求跨粒度比较，且你已经给出统一 tie-break。
10. **`id` 编号从 `01` 开始**，两位数字格式递增，`weight` 固定为 `1`。
11. 生成 JSON 后检查语法合法性（括号匹配、末尾对象无多余逗号）。
12. **对已存在的 `rubrics.md` 修改时，必须先执行 `8.4 修改前备份` 操作**。
