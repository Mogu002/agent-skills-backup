# 剧本驱动合成数据系统 — 搭建指南

将任意业务的仿真数据生成系统从零搭建。核心原则：**单向因果流**（剧本策略 → 微观行为 → 数据沉淀），严禁"倒填答案"。

### ⛔ 三条铁律（贯穿全程，不可违反）

**铁律一：禁止硬编码**
所有业务参数（转化率、补贴金额、价格比、时段系数等）必须集中在 `config.py` 中，通过变量名引用。决策逻辑中绝不允许出现魔法数字（如 `if price > 25` 或 `churn_rate = 0.3`）。硬编码会导致参数调整时遗漏某处，产生内部不一致的数据。

**铁律二：均衡态必须先于剧本开发**
先把"无剧本的基准世界"调到合理水平并固化，再开发剧本层。顺序不可颠倒——若先做剧本，基准参数的每次调整都会影响剧本效果，陷入反复重调的死循环。基准参数固化后，任何剧本只能通过 `config` 覆盖机制修改参数，不能直接修改基准代码。

**铁律三：导出数据不得暗示剧本存在**
最终交付给 Agent 评测的数据（Agent 可见层）必须是一份"看起来完全真实"的业务数据，满足：
- 字段命名和取值域与真实业务无异，无任何 `scenario`、`inject`、`simulated` 等暗示性字样
- 剧本期与非剧本期的数据在统计特征上应自然衔接，不能出现"断层"或异常突变
- 所有随机噪声、异常值、数据波动都应与真实业务规律一致，Agent 不能通过统计检验判断数据是合成的

## 前置：商分侧必须先交付的三项输入

在动任何代码之前，确认这三项已就绪：

| 输入项 | 交付内容 |
|-------|---------|
| **底表** | 字段名 + 字段解释（可基于真实底表抽象简化） |
| **剧本事件** | 异动的真实原因；事件对供需和关键指标的影响方向 |
| **业务逻辑及关键指标** | 核心分析指标；影响供需两侧的关键业务逻辑 |

## 五步工作流

### Step 1：业务建模（开工前，不写代码）

回答**建模三问**，决定系统骨架：

**问题 1：谁是主体，如何交易？**
- 供给侧主体 / 需求侧主体 / 核心交易事件（最小可计量单元）
- 无明确供需两侧 → 单边业务，供给侧退化为"平台产品能力"

**问题 2：主体的核心决策变量是什么？**
- 需求侧：什么让用户选择/放弃这次交易？
- 供给侧：什么让供给者留存/离开平台？
- → 这两个变量是决策漏斗和飞轮的锚点

**问题 3：供需之间是否实时耦合？**

| 耦合类型 | 典型业务 | 主循环处理 |
|---------|---------|----------|
| **实时强耦合**：供需在同一时段互相依赖 | 网约车/外卖/即时零售 | 需要多遍扫描解循环依赖（见 Step 4） |
| **异步弱耦合**：供给提前存在，当天无依赖 | 电商/内容平台 | 顺序执行即可 |
| **单向依赖**：供给固定，只有需求侧决策 | SaaS/会员 | 只模拟需求侧 |

完成后，画出文字版决策漏斗，列出 3-5 个典型剧本类型。

> 如需业务对照参考，见 `references/business-concept-map.md`

### Step 2：参数标定（开发前，先跑均衡态）

1. 确定平衡态目标指标值（参照真实业务数据或商分给出的基准）
2. 用目标值反推 `config.py` 参数
3. 运行纯平衡态模拟（关闭所有剧本），运行验证脚本：
   ```bash
   python scripts/validate_simulation.py <output_dir> --baseline
   ```
4. **查看可视化图表，判断是否平稳**，不达标则调参并重跑——循环直到通过
5. 验证通过后**固化**基准参数，再开发剧本层

**均衡态验证通过标准**：
- 成交转化率在真实业务 ±5% 以内
- 供给侧留存率：30天内不应出现 >20% 的人口骤降
- 需求侧日活跃率：在预设水平 ±10% 范围内波动

**调参迭代闭环**（均衡态未通过时反复执行）：
```
① 合成数据（关闭所有剧本，运行30天）
② 运行验证脚本 → 打开可视化图表
③ 对照以下关键图表判断是否平稳：
   - 供给侧人口曲线（司机/供给方总数随天数变化）→ 不应持续单调上升或骤降
   - 核心收益指标趋势（IPH 等）→ 应在目标区间内小幅波动，不应漂移
   - 成交量/转化率趋势 → 30天内保持基本水平，无持续衰退或爆炸性增长
   - 供需比/等待时间趋势 → 在合理范围内稳定，不应极端偏离
④ 根据图表定位参数：
   - 供给侧持续流失 → 调高收益指标或降低流失率阈值
   - 需求侧持续萎缩 → 调整价格敏感度或基础转化率
   - 飞轮失控（持续放大）→ 检查满意度上限、动量衰减系数
   - 数值漂移但无趋势 → 检查第1天保护期是否生效
⑤ 修改 config.py → 回到步骤①
```
> 每次迭代只改 **1-2 个参数**，避免多参数同时调整导致因果不清。
> 目标是 30 天可视化曲线"看起来平稳"，不是数值精确。达到目标后立即固化参数，进入 Step 3。

---

### Step 3：按模块顺序实现系统（七层架构）

严格按依赖顺序实现，不要跳层：

```
① config.py        ← 全局参数单一真源；所有参数支持 replace/add/multiply 覆盖
② entities.py      ← 供需双侧主体固定画像（仅初始化一次，不修改）
③ decision.py      ← 微观决策漏斗（每笔交易的多阶段概率决策）
④ aggregator.py    ← 聚合：交易明细 → 双侧日表
⑤ dynamic_ecosystem.py   ← 飞轮效应（满意度→留存→供需循环）
⑥ dynamic_supply_pool.py ← 供给侧活跃/预备双层池（仅双边市场需要）
⑦ scenario_manager.py + scenario_config.py ← 剧本编排与运行时管理
⑧ simulator.py    ← 组装主循环
⑨ exporter.py + validator.py ← 导出与验证
```

**各层关键约定**：

**① config.py**：按"市场规模 / 基础行为概率 / 核心决策变量 / 飞轮参数 / 分层系数"五类组织参数。
- **硬编码自查**：完成每一层后，全局搜索 `decision.py`、`ecosystem.py`、`simulator.py` 中的裸数字（正则 `[^a-zA-Z_][0-9]+\.[0-9]+` 或整数字面量），逐一确认是否应提取为 config 变量。概率值、阈值、系数、比率一律不允许硬写在逻辑代码里。

**② entities.py**：需求侧至少含（价格敏感度、时间敏感度、生命周期阶段、所属地域）；供给侧至少含（类型全职/兼职等价物、生命周期阶段）。

**③ decision.py** — 决策漏斗模板：
```
需求产生（冒泡）
  → 阶段1：核心决策变量判断（价格/质量/相关性）  ← 必须
  → 阶段2：体验质量判断（等待/时效）            ← 按业务是否有此维度决定
  → 阶段3：随机转化（基础转化率）               ← 必须
  → 供给匹配判断（是否有供给接单）              ← 按业务是否有此维度决定
  → 成交 / 各类失败
```
- 阶段1：线性流失概率，按敏感度分层设独立上限，防止过度响应
- 阶段2：Sigmoid 函数 `P = base + (max-base) / (1 + e^(-k*(x-x0)))`
- 必须记录 Ground Truth 字段：`_is_submitted`、`_exit_reason`、`_core_decision_variable`

**⑤ dynamic_ecosystem.py** — 飞轮必须建模：
```
成交量 → 供给侧收益指标（等价于 IPH）→ 供给侧满意度 → 流失/激活率
       ↕
        → 需求侧体验指标 → 需求侧满意度 → 活跃率/流失率
       ↕
平台动量（双侧满意度的指数移动平均）
```
- 满意度均衡区间设为 0.5（无剧本时不冲顶）
- 第1天设保护期，禁止任何人口流失

**⑦ scenario_config.py** — 剧本三要素：
- 生效时间：`duration = (start_day, end_day)` 或 `None`（永久）
- 覆盖范围：全局日级 → 地域日级 → 交易级条件覆盖
- 覆盖模式：`REPLACE / ADD / MULTIPLY`

### Step 4：主循环设计

**不需要多遍扫描的业务**（电商/内容/SaaS），主循环：
```
1. 更新剧本配置 → 2. 更新供给侧状态 → 3. 确定当天供给能力
→ 4. 逐需求侧主体执行决策漏斗 → 5. 聚合日表
→ 6. 更新生态状态（满意度/动量/人口）→ 7. 记录供给侧快照
```

**需要多遍扫描的业务**（即时匹配型：网约车/外卖/即时零售），在步骤4处展开为三遍：
```
Step 4A（第一遍）：生成所有需求意向计划（不做决策，不消耗随机数）
Step 4B（第二遍）：轻量价格判断 → 统计估算提单数 → 计算供需比
Step 4C（第三遍）：带入真实供需比，执行完整决策漏斗
```

> 为什么需要三遍：提单数→供需比→价格→提单数 形成循环依赖，必须打破。

---

### Step 5：数据导出与验证

**三层导出**：
- **Agent 可见层**：去除所有 `_` 开头的 Ground Truth 字段
- **验证真相层**：完整保留 Ground Truth 字段
- **分析增强层**：保留关键机制字段（供需比、转化阶段等）

**第1天必须排除**，导出时从第2天开始；题目天数 = 系统天数 - 1，必须显式约定。

运行完整验证：
```bash
python scripts/validate_simulation.py <output_dir> --full
```

**每个剧本验证标准**：能解释"参数 X 从 A→B，导致指标 Y 变化 Z%"。

**数据真实性自检（交付前必做）**：
站在一个"不知道剧本存在"的分析师角度，审视 Agent 可见层的数据：
- [ ] 所有字段名、枚举值是否符合真实业务表的命名规范（无 `_sim`、`_fake`、`scenario` 等字样）
- [ ] 剧本生效日前后，各指标的变化幅度是否在真实业务中可能出现的范围内（非剧本期每日波动 ≤5%，剧本期变化应有业务合理性）
- [ ] 数据的分布特征（均值、方差、偏度）是否与真实业务基准一致
- [ ] 不同维度（地域/时段/用户类型）的交叉数据是否互相自洽，无矛盾
- [ ] 数据中是否存在任何"过于整齐"的数字（如恰好 10000 单、转化率恰好 50%），需引入合理噪声

## 关键经验速查

| 经验 | 核心要点 |
|-----|---------|
| base_config 与运行时 config 分离 | `base_config = deepcopy(original)` 永不随剧本变，基准参照系必须用它 |
| 剧本生效后同步所有子模块 | `_update_modules_config()` 统一更新所有子模块的 config 引用 |
| 交易级覆盖用深拷贝 | 订单级剧本覆盖必须在副本上操作，否则影响同批其他订单 |
| 供需比单位在设计时就固化 | 在 `decision.py` 开头写明公式和单位，阈值都在该单位下标定 |
| 新老用户流失率必须独立 | 共用参数会导致补贴剧本无法区分"拉新"和"留老"两种机制 |
| 均衡态先于剧本开发 | 先标定基准参数，验证通过后固化，再开发剧本 |

> 详细踩坑案例见 `references/design-manual.md`

## 快速启动 Checklist

```
- [ ] 商分三项输入已就绪（底表 / 剧本事件 / 业务逻辑及关键指标）
- [ ] 完成建模三问，有文字版决策漏斗
- [ ] 判断是否需要多遍扫描
- [ ] 设计 TransactionContext 的维度字段
- [ ] 设计供给侧收益指标（等价于 IPH）
- [ ] 设计需求侧敏感度属性（至少：价格敏感度）
- [ ] 确定分层结构（新老用户至少2层）
- [ ] 实现均衡态并用 validate_simulation.py 验证（合成→看可视化→调参，循环直到30天曲线平稳）
- [ ] **均衡态指标通过后，固化基准参数，再开始剧本开发**
- [ ] 实现至少1个"供给侧冲击"剧本 + 1个"竞对环境"剧本
- [ ] 验证 Ground Truth 字段完整性
- [ ] 显式约定并记录第1天排除的口径换算规则
- [ ] 全局搜索逻辑代码中的硬编码数字，确认已全部提取到 config
- [ ] 对 Agent 可见层做数据真实性自检（字段命名/指标波动/数据自洽/噪声合理性）
```
