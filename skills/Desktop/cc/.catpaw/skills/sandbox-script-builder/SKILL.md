# Sandbox Script Builder

## 何时使用

当用户要做下面这些事时，使用这个技能：

- 设计一个新的业务沙盒剧本
- 从业务事件出发，构建可运行的剧本配置
- 拆解剧本中的事件特征、阶段和影响维度
- 把业务语言翻译成现有 config 参数调整
- 推导底表中会出现哪些异常
- 验证剧本是否符合真实业务逻辑
- 为 BA Agent / 商分 / 评测任务编写可归因的剧本
- 输出剧本模板、剧本设计方法或示例剧本

如果用户只是想写一个随意的业务故事，或不关心自变量、因变量、底表和验证链路，不要使用这个技能。

## 默认立场

这个技能的默认目标不是“讲一个好故事”，而是**构建一个完整、可运行、可解释、可验证，并且不越界的剧本**。

始终默认：

- 当前默认基座是《特团MVP业务沙盒 v0.1》；除非用户明确说明已经切换到新版本模型，否则不要擅自泛化到别的业务底座
- 先做 **单剧本、单主矛盾**，再考虑多剧本叠加
- 先做 **边界校验**，再写剧本卡片与阶段
- 先写 **事件特征**，再写参数
- 始终沿 `事件 -> 自变量 -> 中间机制 -> 因变量` 的链路推进
- 先写 **底表异常的形态**，再写验证方案
- 先确保 **可解释和可验证**，再追求复杂度
- 最终输出默认遵循四个一级板块，且使用这四个固定标题：
  - `一、事件特征拆解`
  - `二、自变量调整明细`
  - `三、因变量影响全景`
  - `四、合理性验证方案`
- `二、自变量调整明细` 默认再拆成三个固定维度，且按这个顺序输出：
  - `需求侧`
  - `供给侧`
  - `流量侧`

如果用户提供了截图、表格、样例文档或既有模板，**优先对齐用户给出的列顺序、字段命名、分组方式和板块顺序**；本文件中的模板只作为默认兜底。

## 当前版本硬边界

下面这些不是“可参考建议”，而是**当前特团 MVP 沙盒的白名单边界**。生成剧本时，只要涉及对应板块，就**不能超出这些范围**。

### 总规则

- 优先把用户的业务话术**映射回当前已存在的对象、字段、枚举和值域**，不要先发明新概念
- 如果用户提到的对象超出当前 MVP 范围，先尝试映射到现有字段；映射不了，就明确标注“当前 MVP 暂不支持”，不要硬编
- 如果 `references/examples.md` 的示例写法与本文件的硬边界冲突，**一律以本文件为准**
- 时间、城市、入口、品类、生命周期、用户属性这些板块，默认都按白名单处理，而不是自由扩写

### 1. 仿真时间设置白名单

| 项目 | 当前限定值 | 生成剧本时的规则 |
| --- | --- | --- |
| 仿真总天数 | `31天` | 含 `Day 0` 保护期，不要写成 45 天、60 天、季度仿真或跨多月仿真 |
| 可见导出天数 | `Day 1-30` | 阶段定义、异常观察、验证窗口都必须落在 `Day 1-30` |
| 剧本生效天 | `系统第11天起` | 冲击期默认从 `Day 11` 开始；不要把正式剧本生效写在 `Day 1-10` |

如果用户没有指定阶段时间，默认写成：

- `A / 基线期：Day 1-10`
- `B / 冲击期：Day 11-20`
- `C / 恢复期：Day 21-30`

时间边界规则：

- 基线期默认放在 `Day 1-10`
- 冲击期默认放在 `Day 11` 及之后
- 恢复期默认放在 `Day 21-30`
- 不要把恢复期写到 `Day 30` 之后
- 如果用户只要两阶段，也要保证冲击从 `Day 11-30` 内开始，不得突破总窗口

### 2. 市场规模参数白名单

当前只支持以下 5 个城市和对应盘子：

| 城市 | 初始档口数 | 初始用户池 | 城市系数 |
| --- | --- | --- | --- |
| 北京 | `40` | `80,000` | `1.2` |
| 上海 | `50` | `100,000` | `1.3` |
| 成都 | `45` | `90,000` | `1.1` |
| 武汉 | `35` | `70,000` | `0.95` |
| 郑州 | `30` | `60,000` | `0.85` |

全平台合计：

- `200` 个档口
- `400,000` 用户池

市场规模规则：

- 不要发明第六个城市
- 不要把当前模型写成“全国盘”“全省盘”或新的城市集合
- 不要把初始盘子扩写成超出当前白名单的城市档口数 / 用户池 / 城市系数
- 如果用户想表达“高线城市/低线城市差异”，优先在上述 5 城里选对应城市切片，不要新增城市层级

### 3. 流量入口白名单

当前流量入口只使用这 5 个枚举：

| 展示名称 | 枚举值 | 基线流量占比 |
| --- | --- | --- |
| 猜喜高卡 | `main_feeds_high_card` | `45%` |
| 猜喜低卡 | `main_feeds_low_card` | `20%` |
| 搜索 | `search` | `18%` |
| 大团购 | `group_purchase` | `12%` |
| 社群/BD地推 | `community_bd` | `5%` |

流量规则：

- 写流量侧剧本时，优先使用以上 5 个入口名和枚举值
- 不要额外创造 `feed_banner`、`short_video`、`coupon_center` 之类当前模型里没有的入口
- 如果用户想表达新的流量来源，先尝试映射到上述入口之一；映射不了，就明确说当前 MVP 未建模

### 4. 商品类型白名单

当前商品层只支持以下范围：

- 每个档口的商品数：**指数分布采样，均值 `3.5`，上限 `8` 个商品/档口**
- 当前只支持 3 个品类：

| 品类名称 | 枚举值 | 档口内占比 | 团购价均值 | 划线价均值 | 拉新能力 | GTV贡献 |
| --- | --- | --- | --- | --- | --- | --- |
| 奶茶咖啡 | `milk_tea_coffee` | `40%` | `12` 元 | `22` 元 | `0.70` | `20%` |
| 西式快餐 | `western_fast` | `35%` | `22` 元 | `38` 元 | `0.50` | `30%` |
| 正餐 | `main_meal` | `25%` | `42` 元 | `68` 元 | `0.20` | `50%` |

商品规则：

- 不要新增第四个品类，如水果、生鲜、夜宵、小吃、烘焙等，除非先明确映射到现有 3 个品类之一
- 不要把“商品类型”写成开放标签池
- 若用户想表达品类结构变化，只能在这 3 个品类之间调权重或调相关价格/补贴/流量参数
- `sale_price`、`market_price`、`discount_rate` 的解释要围绕当前 3 品类展开，不要凭空增加新的价格带体系

### 5. 用户生命周期与用户属性白名单

当前用户生命周期只支持以下 3 类：

| 生命周期 | 枚举值 | 初始占比 | 日活跃率 |
| --- | --- | --- | --- |
| 新客 | `new_user` | `15%` | `12%` |
| 低频老客 | `low_freq` | `26.2%` | `8%` |
| 规律买用户 | `regular_buyer` | `58.8%` | `25%` |

当前用户属性只支持以下范围：

| 属性 | 当前限定值 | 生成剧本时的规则 |
| --- | --- | --- |
| `_price_sensitivity` | `new_user=0.85`、`low_freq=0.60`、`regular_buyer=0.35`，并叠加高斯噪声 `σ=0.08` 后截断到 `[0,1]` | 可以用来解释价格敏感差异，但不要再发明新的原生用户标签 |
| `_preferred_category` | 从 `milk_tea_coffee / western_fast / main_meal` 中均匀随机选一个 | 不要新增第四种偏好品类 |
| `join_day` 历史偏移 | `0` 到 `-20` 天 | 用于分散新客 21 天存活期到期点，不要写成更长历史窗 |
| 新客存活期 | `21天` | 不要把新客自然存活期改成 45 天、60 天等新机制 |
| 新客晋升条件 | `7天内有成单 -> 晋升 low_freq` | 若写生命周期改善，先围绕已有晋升逻辑展开 |
| 生命周期迁移概率 | `low_freq -> regular_buyer = 1.8%/天`；`regular_buyer -> low_freq = 0.8%/天` | 不要自造新的生命周期状态或跳转规则 |

用户规则：

- 不要把用户原生分层扩成学生、白领、宝妈、游客等新生命周期枚举
- 如果用户想表达“价格敏感人群”“奶茶偏好人群”，优先映射到 `_price_sensitivity` 或 `_preferred_category`，而不是新增字段
- `_price_sensitivity`、`_preferred_category`、`join_day` 默认属于**生成机制或解释机制字段**，不是优先给分析师看的主观察字段

### 6. 字段角色边界

字段使用时再额外遵守这些规则：

- 自变量优先来自 `config` / `Scenario overrides` / 初始化参数，不要直接改结果字段
- 因变量优先来自 `dwd_transaction`、`dws_user_daily`、`dws_stall_daily`、`dws_platform_daily`
- GT / 内部机制字段默认只用于解释和验证，不默认写成题面主观察字段
- 任何看起来像“新业务对象”“新标签体系”“新枚举值”的内容，都先问自己：能否映射回当前白名单；若不能，就不要写进剧本正文

## 开始前先读什么

如果工作区里存在下面这些资料，先读再写：

- `业务沙盒项目整理.md`
- 与当前业务场景相关的沙盒设计文档
- 已有底表说明、schema、字段字典
- 现有剧本设计文档
- 评测题样例、真值层说明、`scenario_log` 说明
- 当前 skill 下的 `references/examples.md`（需要示例剧本、模板或对照样例时使用）
- 当前 skill 下的 `references/variable-classification.md`（需要确认剧本该用哪些字段、字段业务含义、生成机制、因果链与字段对应关系时使用）

如果用户已经给出学城文档或明确版本，优先对齐该版本文档；当前默认对齐《特团MVP业务沙盒 v0.1》。如果资料不完整，也不要卡住；先按最小可用版本写出一版，并显式标注假设。

## 标准 SOP

按下面顺序工作，不要跳步。

### 0. 先做边界闸门

正式写剧本前，先快速过一遍这 6 个问题：

- 时间窗口是否落在 `Day 1-30`，且冲击是否从 `Day 11` 及之后开始
- 城市是否只使用北京 / 上海 / 成都 / 武汉 / 郑州
- 流量入口是否只使用 5 个现有入口枚举
- 商品是否只使用 3 个现有品类
- 用户生命周期是否只使用 `new_user / low_freq / regular_buyer`
- 用户属性、机制参数、观察字段是否仍然落在当前白名单内

处理规则：

- 能映射就映射，例如把“咖啡偏好人群”映射到 `_preferred_category = milk_tea_coffee`
- 映射不了就收紧，不要硬造字段
- 只有边界过关后，才继续写四段式正文

### 1. 先定义剧本卡片、目标与阶段

先明确：

- 这次要模拟的业务事件是什么
- 所属业务场景是什么
- 这是需求侧、供给侧、流量侧、双侧、平台动作还是外部竞争事件
- 本次是否只做一个剧本
- 剧本是否分阶段（基线 / 冲击 / 恢复）
- 最终是否要严格对齐某张图、某个表头、某个样例格式
- 这个剧本会动到哪些白名单实体：时间、城市、入口、品类、生命周期、用户属性

如果用户没有说明，默认：

- 先做一个剧本
- 先做三阶段：`Day 1-10 / Day 11-20 / Day 21-30`
- 先选择一个主影响方向，不混入多个平级主因
- 阶段名默认可写为 `A / 基线期`、`B / 冲击期`、`C / 恢复期`

### 2. 产出 `一、事件特征拆解`

把事件拆成可以被系统模拟的特征，不要停留在自然语言故事层。

默认优先写成**表格**，而不是散点描述。推荐至少包含这些列：

- `阶段`
- `事件特征`
- `影响维度`
- `现实对应`
- `在沙盒中的表现`

其中 `影响维度` 默认只使用这四类值：

- `需求侧`
- `供给侧`
- `流量侧`
- `需求侧+供给侧`

至少拆这五类信息：

- **阶段**：基线 / 冲击 / 恢复分别发生什么
- **事件特征**：把业务事件拆成可模拟的单条特征
- **影响维度**：这条特征首先打在需求、供给，还是双侧联动
- **现实对应**：现实业务里到底发生了什么，不要只写抽象概念
- **在沙盒中的表现**：这条现实变化会在沙盒里如何落成参数扰动、结构变化或可见异常

输出规则：

- 一行只表达一个可模拟的特征，不要一行塞多个平级主因
- `影响维度` 不要写成自由文本；默认只从 `需求侧 / 供给侧 / 流量侧 / 需求侧+供给侧` 四选一
- 入口权重、CTR、卡位、曝光分配类冲击，优先标成 `流量侧`，不要硬塞进需求侧或供给侧
- `现实对应` 要写真实业务动作、真实业务状态或真实经营现象，不要只复述表面指标
- `在沙盒中的表现` 要写成参数变化、结构变化或阶段性异常
- 如果提到城市、入口、品类、用户分层，必须优先使用当前白名单名称
- 如果用户给了图片模板，优先沿用图片里的阶段分块和列命名

### 3. 产出 `二、自变量调整明细`

把业务语言翻成系统里**已经存在的** config / `Scenario overrides` 参数，不要自造一层新的字段名。

默认优先写成**按维度分组的表格**，不是把所有参数摊平成一张无分类长表。

默认在 `二、自变量调整明细` 下再拆三个固定子分组，并按这个顺序输出：

1. `需求侧`
2. `供给侧`
3. `流量侧`

如果用户提供了截图、表头或样例格式，优先对齐用户的分组呈现方式；否则默认使用上面的顺序。分组可以用**分组标题 + 子表**，也可以用**一张总表中的分组行**，但必须显式体现这三类维度。

每个子分组优先复用同一套列：

- `自变量`
- `基线值`
- `冲击期剧本值`
- `恢复期剧本值`
- `影响路径`

必要时可补充：

- `生效对象`
- `调整理由`
- `参数来源`

每个自变量至少写清：

- 参数名
- 基线值
- 分阶段剧本值
- 生效阶段
- 生效对象
- 调整理由或影响路径

优先按下面三个维度找参数：

- **需求侧**：活跃率 / 流入率 / 流失率 / 生命周期迁移 / 节假日自然活跃类参数
- **供给侧**：供给规模 / 在线率 / 匹配率 / 外部压力 / 风险阈值 / 供给相关价格与货盘结构
- **流量侧**：入口流量权重 / CTR / 分发卡位 / 曝光分配 / 对点击转化起量的补贴或触达参数

分类判断规则：

- 先影响 `is_active`、流入、生命周期的，归 `需求侧`
- 先影响供给池、在线、匹配、商家状态的，归 `供给侧`
- 先影响入口分发、曝光、点击、CTR/CVR 起量的，归 `流量侧`
- 若同一参数同时作用多侧，按**第一跳传导链**归类，不要在多个分组重复出现

默认先去 `references/variable-classification.md` 里找**真实可控自变量**、**真实可观测因变量**、**状态变量 / GT 字段**及它们的对应关系，优先用现成字段构建剧本，不要先发明新字段。

如果你开始想把 `order_cnt`、`gmv`、`ctr_eff`、`subsidy_roi` 这类结果字段直接当参数改，先停下来读 `references/variable-classification.md`；默认只把 `config` / `overrides` 层可直接控制的量写成自变量。

输出规则：

- 默认按 `需求侧 -> 供给侧 -> 流量侧` 顺序输出
- 每个分组内一行只写一个真实参数
- 如果某一维度没有关键调整项，默认保留该分组并写 `无关键调整`，除非用户明确要求省略
- 默认同时给出基线值和分阶段剧本值；没有恢复期就写 `-`
- `影响路径` 优先写成 `参数 -> 中间状态 -> 底表指标` 的短链路
- 如果一句业务话找不到对应参数，先不要继续写因变量，先补参数映射
- 只要涉及城市、入口、品类、生命周期或用户属性，参数取值和生效对象都不能超出本文件白名单

### 4. 产出 `三、因变量影响全景`

从“参数怎么改”继续往下推，写出底表里会看到什么异常。

默认优先写成**表格**，并且**按底表 / 数据层分组**。推荐至少包含这些列：

- `底表`
- `因变量`
- `性质`
- `基线/对照`
- `冲击期表现`
- `恢复期表现`
- `影响机制`

优先按表分层写：

- `dwd_transaction`：曝光、点击、成交、入口结构、价格、补贴等
- `dws_user_daily`：活跃用户、新客、老客、生命周期、流失 / 降级等
- `dws_stall_daily`：商家 / 档口收入、风险状态、在线商品数、满意度等
- `dws_platform_daily`：总曝光、总订单、GMV、客单价、ROI、动量等

如果当前场景不是这四张表，也要沿用“事件级 / 用户侧 / 供给侧 / 平台侧”的分层思路。

输出规则：

- 一行聚焦一个因变量，不要把整张表的所有结论堆在一格里
- `性质` 优先写清这是总量异常、结构异常、时序滞后、恢复过冲，还是仅新增样本受影响
- `影响机制` 要能回连到前面的参数变化，而不是只写“因为节日 / 因为竞争”
- `基线/对照` 用于说明正常状态，避免只有坏结果没有参照
- 恢复期若不存在，可以写 `-`，但不要省掉该列
- 主观察字段优先使用 agent 可见层字段；GT / 内部机制字段默认只放在解释或验证里

### 5. 产出 `四、合理性验证方案`

验证不只是写“方向合理”，而是要给出**可执行的检查方案**。

默认优先写成**表格**。推荐至少包含这些列：

- `验证维度`
- `预期结果`
- `验证方法`
- `判定标准`

至少做下面五类检查：

- **方向验证**：变化方向是否符合常识
- **量级验证**：幅度是否过大或过小
- **时序验证**：冲击、恢复、滞后是否合理
- **鉴别性验证**：能否和其他剧本区分开
- **多表一致性验证**：多张底表是否互相印证

如果工作区里存在真值层或 `scenario_log`，还要补：

- 真值校验
- 阶段切片验证
- 可视化趋势验证

输出规则：

- `验证方法` 要能落地到对比方式、切片方式或表间交叉验证方法
- `判定标准` 尽量写阈值、范围或“满足什么现象才算通过”
- 不要只写抽象判断句，例如“看起来合理”“基本符合预期”
- 时间切片、城市切片、品类切片、生命周期切片都不能超出白名单范围

### 6. 收口与自检

最终交付时，默认结构应是：

- 剧本名称
- 剧本类型
- 阶段定义
- `一、事件特征拆解`
- `二、自变量调整明细`
- `三、因变量影响全景`
- `四、合理性验证方案`

如果用户明确要示例，优先参考 `references/examples.md` 示例剧本，但最终结构仍优先对齐用户给的图或本文件模板，并且**不能突破本文件硬边界**。

## 重要 gotchas

这些坑要在主文件里前置，不要等失败后才意识到：

- 不要一上来写多因素混合剧本；默认先做单主因剧本
- 不要在边界检查之前就开始编参数
- 不要把剧本生效写在 `Day 11` 之前
- 不要把阶段写到 `Day 30` 之外
- 不要发明第六个城市或新的城市系数
- 不要新增第四个商品品类
- 不要新增新的生命周期枚举或用户标签体系
- 不要把 `_preferred_category`、`_price_sensitivity` 这类生成机制字段直接写成分析师主观察位
- 不要只写“结果会变差”，必须写清楚改了哪些参数
- 不要只写参数，不写底表异常；没有底表异常就不可评
- 不要把 dwd / dws 底表中的结果字段直接当作自变量；多数可见异常都属于因变量
- 不要自造一层概念字段替代真实参数名 / 真实底表字段名；能写现有字段名时就直接写现有字段名
- 不要跳过基线期；没有基线就没有对照
- 不要让恢复期瞬间满血；真实业务通常存在恢复滞后
- 不要让剧本无法区分；必须写一个关键鉴别特征
- 不要把 `影响维度` 写成开放描述；默认只能写 `需求侧 / 供给侧 / 流量侧 / 需求侧+供给侧`
- 不要把入口权重、CTR、卡位、曝光分配类冲击误写成需求侧或供给侧；默认归 `流量侧`
- 不要把“现实对应”和“在沙盒中的表现”写成同一句空泛复述；前者写真实世界，后者写沙盒落地方式
- 不要把供给侧问题、需求侧问题、流量侧问题和双侧问题混成一团
- 不要只写“上升/下降”，要写清这是总量异常、结构偏移、恢复滞后还是过冲恢复
- 不要只验证一张表；至少检查事件层、用户层、平台层是否一致
- 不要把需求侧、供给侧、流量侧参数混排成一张无分组长表；`二、自变量调整明细` 必须显式分组
- 不要在多个分组里重复摆放同一个参数；默认按第一跳传导链归一个主类
- 不要再把“关键传导路径”“验收标准”等内容拆成与四大板块平级的一级标题；应折叠进四段式结构内部
- 不要把四个一级板块写成纯大段 prose；默认优先用表格承载
- 如果用户给了截图 / 样例表头，先对齐列顺序、分组方式和命名，再填内容

## 何时停止扩写

当下面这些内容已经清楚时，就先停，不要为了显得完整继续堆字：

- 剧本主因明确
- 阶段划分明确
- 四个一级板块齐全
- 参数映射明确
- 底表异常明确
- 验证方法明确
- 所有涉及的对象都在当前白名单边界内

如果用户没有要求，不要自动扩展成多剧本矩阵、批量题库设计或完整平台方案。

## 最小验证闭环

交付前至少做一次脑内 dry-run：

- 用一句用户话，检查这个 skill 会不会命中：例如“帮我设计一个竞对补贴战剧本”
- 假设另一个 agent 只读本文件，确认它知道第一步该先做边界闸门，而不是直接编参数
- 用一个代表性请求自测：是否能顺着“边界校验 -> 事件特征 -> 自变量 -> 因变量 -> 验证”一路走通
- 检查最终输出是否真的出现这四个一级标题，而不是退回旧的八段式结构
- 检查时间、城市、入口、品类、生命周期、用户属性是否有任何一项越界
- 检查入口权重、CTR、卡位、曝光分配类冲击是否被正确归到 `流量侧`，以及因变量表里是否写清异常形态

如果发现默认路径不清、输出太散、结构不对齐用户样例，或剧本与故事写作混淆，就先收紧再交付。
