# WBS Task Breakdown

## 何时使用

当用户希望把一个复杂目标拆成更清晰、更可执行的结构时，使用这个 Skill。

典型触发方式：
- “帮我做一个 WBS 分解”
- “把这个复杂任务拆开”
- “给我一个执行计划/实施计划”
- “把需求拆成阶段和子任务”
- “整理成里程碑、工作包、依赖关系”
- “帮我规划这个项目怎么推进”

如果用户只是问某个概念，或任务非常简单，不要强行套用完整 WBS。
如果用户明确要求直接执行代码或落地变更，不要只停留在拆解；应先给出拆解，再继续执行最合理的下一步。

## 核心目标

把模糊的大任务整理成：
- 目标清晰
- 范围明确
- 分层合理
- 工作包可执行
- 依赖可识别
- 验收可检查

## 工作原则

1. 先看目标和交付物，再拆动作。
2. 按“项目/阶段/工作包/具体任务”逐层拆解。
3. 每层尽量避免重复，整体上尽量覆盖完整。
4. 不臆造未知事实；缺失信息用“假设”标出。
5. 单个工作包应边界清晰，能被独立安排和跟踪。
6. 优先输出能帮助决策和执行的拆解，而不是空泛分类。
7. 如果任务与代码、设计、运营、文档等多角色协作相关，要显式标出跨角色依赖。

## 默认拆解流程

按下面顺序处理：

1. **识别目标**
   - 提炼用户最终想达成的结果。
   - 区分“目标”“约束”“现状问题”“交付物”。

2. **划定范围**
   - 标出本次包含和不包含的内容。
   - 如果范围不清，给出最保守、最合理的边界假设。

3. **确定一级结构**
   - 优先按交付阶段或关键结果拆一级项。
   - 常见一级维度：调研、方案、设计、开发、测试、发布、运营。
   - 如果是非软件任务，也可以按准备、执行、验收、复盘来拆。

4. **细化为工作包**
   - 每个一级项继续拆成可执行工作包。
   - 工作包应尽量包含：产出、前置条件、关键动作、完成标准。

5. **补齐执行信息**
   - 为重要工作包补充依赖、风险、优先级、并行关系。
   - 必要时补一版建议执行顺序。

6. **自检拆解质量**
   - 是否有明显遗漏。
   - 是否存在重复项或边界重叠。
   - 是否已经拆到“可分配、可跟踪、可验收”的粒度。

## 粒度控制

默认拆到“工作包”层级即可，不必无限细化。
当用户明确要求更细时，再继续拆到“具体任务”层。

可参考以下判断：
- 还不能分配给具体负责人：继续拆。
- 还无法估算工作量：继续拆。
- 还无法判断是否完成：继续拆。
- 已经能独立推进且验收明确：停止拆解。

## 输出策略

### 默认输出

默认输出 5 个部分：
1. `任务目标`
2. `范围与假设`
3. `WBS 分解`
4. `关键依赖与风险`
5. `建议执行顺序`

### 简版输出

如果用户只想“快速拆一下”，输出：
- 目标
- 3-7 个一级项
- 每个一级项下 2-5 个工作包
- 最后补一段执行建议

### 深度版输出

如果用户明确提到“详细版/项目计划/可落地执行”，额外补充：
- 每个工作包的输出物
- 前置依赖
- 验收标准
- 优先级或里程碑
- 待确认问题

## 输出模板

```text
任务目标：
- <最终要达成的结果>

范围与假设：
- 包含：<本次纳入的范围>
- 不包含：<本次不处理的内容>
- 假设：<基于当前信息做出的合理假设>

WBS 分解：
1. <一级项 1>
   1.1 <工作包>
   1.2 <工作包>
   1.3 <工作包>
2. <一级项 2>
   2.1 <工作包>
   2.2 <工作包>
3. <一级项 3>
   3.1 <工作包>
   3.2 <工作包>

关键依赖与风险：
- 依赖：<前置条件、外部协作、资源约束>
- 风险：<范围变动、信息不足、时间风险、质量风险>

建议执行顺序：
1. <先做什么>
2. <再做什么>
3. <最后做什么>
```

## 深度版模板

当用户需要更完整的执行拆解时，使用这个结构：

```text
任务目标：
- <最终目标>

范围与边界：
- 包含：<范围>
- 不包含：<范围外内容>
- 关键约束：<时间、资源、技术、预算、依赖>
- 关键假设：<假设>

WBS 分解：
1. <阶段/交付物>
   1.1 <工作包>
   - 输出物：<交付结果>
   - 前置依赖：<依赖>
   - 验收标准：<如何判定完成>
   1.2 <工作包>
   - 输出物：<交付结果>
   - 前置依赖：<依赖>
   - 验收标准：<如何判定完成>
2. <阶段/交付物>
   2.1 <工作包>
   - 输出物：<交付结果>
   - 前置依赖：<依赖>
   - 验收标准：<如何判定完成>

关键依赖与风险：
- 依赖 1：<说明>
- 依赖 2：<说明>
- 风险 1：<说明>
- 风险 2：<说明>

建议执行顺序：
1. <步骤>
2. <步骤>
3. <步骤>

待确认问题：
- <仍需用户补充的信息>
```

## 场景化拆解建议

### 软件/研发任务

优先按以下维度拆：
- 需求澄清
- 方案设计
- 前后端实现
- 联调测试
- 发布验收
- 数据监控/复盘

如果任务与现有代码库有关，先结合仓库结构、已有模块、约束条件再拆，不要脱离实际工程上下文空拆。

### 产品/运营任务

优先按以下维度拆：
- 目标定义
- 资源准备
- 内容或物料准备
- 执行落地
- 数据回收
- 复盘优化

### 学习/个人复杂事项

优先按以下维度拆：
- 目标拆分
- 前置准备
- 阶段执行
- 检查验收
- 复盘迭代

## 写作要求

- 默认中文输出。
- 结构化、可扫描，避免长段空话。
- 用词稳定：统一使用“阶段 / 工作包 / 依赖 / 风险 / 验收标准”。
- 如果用户没有提供充分信息，不要卡住，先给出带假设的可执行版本。
- 如果一个任务明显可以并行推进，要显式写出可并行部分。
- 如果用户后续要你继续执行，优先从风险最低、依赖最少的工作包开始。

## 示例

### 示例 1：开发一个新功能

用户输入：
> 帮我把“会员积分商城”做个 WBS 分解

应输出为类似：

```text
任务目标：
- 完成会员积分商城从需求到上线的整体落地。

范围与假设：
- 包含：需求、设计、开发、测试、上线。
- 不包含：长期运营活动策划。
- 假设：已有基础用户系统和积分账户能力。

WBS 分解：
1. 需求与方案
   1.1 梳理积分商城核心流程
   1.2 明确商品、兑换、库存、订单规则
   1.3 输出产品方案与边界说明
2. 设计准备
   2.1 输出页面原型
   2.2 确认视觉稿与交互稿
3. 研发实现
   3.1 商品列表与详情开发
   3.2 兑换流程开发
   3.3 库存与订单状态处理
4. 测试与上线
   4.1 联调测试
   4.2 回归测试
   4.3 发布上线与监控

关键依赖与风险：
- 依赖：积分账户接口、库存服务、订单能力。
- 风险：兑换规则变动、库存一致性问题。

建议执行顺序：
1. 先完成需求边界确认。
2. 再推进设计与后端能力确认。
3. 最后进行前后端实现、联调和上线。
```

### 示例 2：非技术复杂任务

用户输入：
> 帮我把一次 200 人线下分享会拆成 WBS

处理方式：
- 先确定目标、时间、场地、预算等关键约束。
- 一级项可拆为：策划、场地、嘉宾、宣传、执行、复盘。
- 每项继续拆成工作包，并补充依赖和时间风险。
